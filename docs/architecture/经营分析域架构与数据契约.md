# 经营分析域架构与数据契约

> **文档状态**：第一阶段已落地，第二阶段已接入生产产能只读聚合、导出和明细钻取接口，第三阶段已补齐品质报废事实契约、处置命令和质量批次数量结算事实；投入/完工/合格/报废的统一覆盖口径仍待补齐
> **确认日期**：2026-07-23
> **适用范围**：生产产能、品质报废、客户与销售等跨域分析能力
> **当前原则**：先确定领域边界与数据口径，再实现统计接口和正式页面；已落地的路由不保留旧兼容跳转，当前不部署。

## 1. 决策结论

月产能统计不放在首页，也不直接挂在生产管理下的“计划中心”或“生产协同”中。

系统新增独立一级域：

```text
经营分析
```

原因是该能力同时读取：

- 生产计划、生产任务、完工记录；
- 销售订单中的客户与订单关联；
- 品质管理中的检验、异常和报废数据。

生产管理、销售管理和品质管理继续各自维护本域事实数据；经营分析只负责跨域读取、汇总、筛选、对比和趋势展示。

## 2. 目标菜单结构

最终菜单建议为：

```text
经营分析
├─ 生产分析
│  ├─ 月产能分析
│  ├─ 产能负荷分析
│  └─ 生产效率分析
├─ 品质分析
│  ├─ 报废分析
│  └─ 不良趋势分析
└─ 客户与销售
   ├─ 订单分析
   └─ 客户分析
```

### 2.1 路由规划

经营分析使用统一路由前缀：

```text
/business-analysis
/business-analysis/production-capacity
/business-analysis/scrap
/business-analysis/orders
/business-analysis/customers
```

路由已按统一前缀落地，作为正式路由，不添加旧路由兼容跳转。当前项目尚未正式接入生产，因此本次可以一次性完成菜单、权限、路由和前端入口的切换。三级菜单代表业务域，页签只从当前路由所属域的页签定义中投影；未映射路由不显示任何页签，禁止使用其他域的默认页签兜底。

现有 `/sales-analysis` 已在第一阶段归并到 `/business-analysis/orders`，并从销售管理菜单和路由树中移除，避免长期存在两个分析入口。

## 3. 与现有模块的职责边界

| 模块 | 负责内容 | 不负责内容 |
| --- | --- | --- |
| 生产管理 / 计划中心 | 计划编制、排产、计划状态和任务执行 | 跨域报废率、客户维度经营报表 |
| 生产管理 / 生产协同 | 现场协作、生产架构、计件等执行能力 | 跨域历史趋势和经营比较 |
| 销售管理 | 客户、订单、订单行、销售履约事实 | 生产产能和品质报废事实 |
| 品质管理 | 检验、质量异常、不合格处置和报废事实 | 生产计划达成率和客户经营排名 |
| 经营分析 | 跨域只读汇总、筛选、趋势、排行、钻取 | 创建或修改生产、订单、品质事实 |
| 首页仪表盘 | 少量实时 KPI、告警和进入分析的入口 | 复杂筛选、长表格、完整历史分析 |

这条边界必须保持：分析页面不能为了方便直接在生产模块或品质模块里复制一套统计逻辑。

## 4. 当前代码现状与不可直接复用点

### 4.1 生产日历的“月统计”当前不是正式月统计

相关文件：

- `src/features/production-calendar/services/production-calendar-service.ts`
- `server/handlers/production_plans.go`
- `server/models/production_plan.go`

当前 `ProductionCalendarService.getMonthlyStats()`：

1. 接收了月份参数，但没有将月份传给接口；
2. 调用 `/production/stats`；
3. 将后端的 `completedToday` 映射成 `totalOutput`。

因此它目前只能作为首页/日历的占位汇总，不能直接作为月产能报表的数据源。

### 4.2 APS 产能指标是运行时估算，不是历史产能事实

相关文件：

- `src/features/aps-scheduling/utils/aps-capacity-metrics.ts`
- `src/features/aps-scheduling/adapters/aps-scheduling.adapter.ts`

当前指标根据任务时间、产线数量、固定班次小时数和任务状态估算 `capacityRate`。它适合展示排产运行压力，不等于某月实际可用产能、实际产出或产能利用率。

经营分析页面可以引用 APS 的排产快照，但必须标记为“计划估算”或“运行时估算”，不能与实际完工数据混为一谈。

### 4.3 品质报废事实契约

相关文件：

- `server/models/quality.go`
- `server/handlers/quality_dto.go`

第三阶段已将品质异常作为报废事实的唯一维护入口。质量异常现在增量提供：

- `TaskID`
- `Severity`
- `DisposalMethod`
- `Status`
- `ScrapQuantity`
- `ScrapUnit`
- `ProductionPlanID`
- `OrderID`
- `ProductID`
- `BatchNo`
- `OccurredAt`

检验任务包含：

- `BatchNo`
- `ProductID`
- `ProductionPlanID`
- `OrderID`
- `SampleQty`
- `Result`

品质处置命令：

```text
POST /api/v1/quality/abnormalities/:id/disposal
```

请求至少应包含：

```json
{
  "disposalMethod": "SCRAP",
  "scrapQuantity": 2,
  "scrapUnit": "pcs",
  "productionPlanId": "…",
  "orderId": "…",
  "productId": "…",
  "batchNo": "…",
  "occurredAt": "2026-07-23T10:00:00Z"
}
```

约束：

- `SCRAP` 必须有大于零的 `scrapQuantity` 和非空 `scrapUnit`；
- `REWORK`、`CONCESSION` 会清除报废数量和单位，避免被分析误计；
- 非上述三种处置方式会被拒绝；
- `occurredAt` 缺失时由品质服务补写当前时间，旧记录不回填；
- 缺少生产关联的旧记录仍可读取，但经营分析会在 `dataQuality` 中标记；
- 所有处置写入通过品质服务统一审计，不允许分析域直接写入。

因此“报废异常记录数”仍不能直接当作“报废数量”。只有数量、单位和关联满足契约的记录，才会进入经营分析的 `summary.scrapQuantity`。

## 5. 月产能分析的数据口径

页面必须明确区分以下指标：

| 指标 | 定义 | 权威来源 |
| --- | --- | --- |
| 计划量 | 选定月份内纳入统计范围的生产计划数量 | 生产计划/工单 |
| 实际完工量 | 选定月份内实际完成的生产数量 | 生产任务或完工记录 |
| 合格量 | 通过品质判定、可进入后续流程的数量 | 品质批次数量结算事实 |
| 报废量 | 品质流程确认的报废数量 | 品质报废记录 |
| 计划达成率 | 实际完工量 / 计划量 | 分析服务计算 |
| 良率 | 合格量 / 总投入量 | 分析服务计算 |
| 报废率 | 报废量 / 总投入量 | 分析服务计算 |
| 产能利用率 | 实际有效产出 / 期间可用产能 | 生产日历、产线能力和完工事实 |

“月产能”不能只显示一个没有口径的百分比。页面至少要能同时看到计划量、实际完工量、合格量、报废量和计算口径。

### 5.1 质量批次数量结算事实契约

质量数量由品质域确认，经营分析只读聚合，不再从抽检量、完工量或报废量反推。

事实表：

```text
quality_batch_quantity_settlements
```

稳定唯一键：

```text
productionPlanId + batchNo
```

每条结算事实必须同时记录：

- `productionPlanId`、`productId`、`batchNo`：稳定生产批次关联；
- `inspectionTaskId`：产生结算的检验任务；
- `inputQuantity`：本批次实际投入量；
- `qualifiedQuantity`：确认合格、可进入后续流程的数量；
- `rejectedQuantity`：确认报废数量；
- `reworkQuantity`：确认返工数量；
- `quantityUnit`：上述数量的统一计量单位；
- `occurredAt`、`confirmedAt`、`confirmedBy`：发生时间与责任审计字段。

硬性约束：

```text
inputQuantity > 0
inputQuantity = qualifiedQuantity + rejectedQuantity + reworkQuantity
```

检验任务必须已完成判定，且任务中的生产计划、产品和批次必须与结算请求一致。相同生产计划和批次重复提交时只更新同一条事实，不产生第二条可被重复统计的记录。

前端在品质检验任务上提供“确认合格并录入数量/录入质量数量”入口；没有稳定生产计划或产品关联时按钮显示但置灰，并提示缺少关联。`SampleQty` 仍明确表示抽检量，只用于检验任务本身，不能替代投入量或合格量。

经营分析规则：

- `summary.qualifiedQuantity` 只读取结算事实中的 `qualifiedQuantity`；
- 只要范围内存在缺失或无效结算事实，`qualifiedQuantity` 仍返回 `null`，并保留 `QUALITY_QUALIFIED_QUANTITY_MISSING`；
- `yieldRate` 与 `scrapRate` 继续返回 `null`，直到投入、完工、合格、报废四类事实完成统一覆盖和单位换算；
- 不允许使用 `InspectionTask.SampleQty`、`ProductionTask.ActualQty` 或“完工量减报废量”推导合格量。

该契约只描述品质数量结算，不改变生产订单、产品或一维码状态链路；生产执行仍由生产域负责，质量事实只作为后续分析和追溯的独立输入。

## 6. 跨域关联键要求

经营分析不得在浏览器中分别请求多个列表后进行不受控的客户端拼接。后端统计服务应基于稳定关联键完成聚合。

最低关联链路：

```text
生产计划
  ├─ orderId ───────> 销售订单 ───────> customerId / customerName
  ├─ productId ─────> 产品档案
  ├─ taskId / batchNo
  └─ productionDate / completedAt

品质检验/报废记录
  ├─ productionPlanId 或 orderId
  ├─ batchNo
  ├─ productId
  ├─ scrapQuantity / unit
  └─ occurredAt
```

如果某条品质记录无法关联到生产计划、订单或批次，接口必须返回数据完整性信息，不得静默归入“未知”后直接参与正式比例计算。

建议接口返回：

```json
{
  "filters": {
    "from": "2026-07-01",
    "to": "2026-07-31",
    "customerId": null,
    "productId": null
  },
  "summary": {
    "plannedQuantity": 0,
    "completedQuantity": 0,
    "qualifiedQuantity": null,
    "scrapQuantity": null,
    "achievementRate": null,
    "yieldRate": null,
    "scrapRate": null
  },
  "breakdowns": {
    "byProduct": [],
    "byCustomer": [],
    "byDay": []
  },
  "dataQuality": {
    "unlinkedQualityRecords": 0,
    "missingQuantityRecords": 0,
    "isComplete": false
  }
}
```

接口名称和字段最终以服务端实现为准，但必须保持“分析接口负责聚合，领域接口负责事实”的分层。

当前服务的日期口径：

- 计划量按生产计划的 `StartDate` 归属月份；
- `StartDate` 为空时，回退到生产计划 `CreatedAt`；
- 完工量只统计 `ProductionTask.Status = DONE`、有 `CompletedAt` 且 `ActualQty` 大于等于零的任务；
- 完工任务按 `CompletedAt` 归属日期，不使用“今日完成量”代替月度统计；
- 客户维度通过生产计划 `OrderID -> SalesOrder.CustomerID/CustomerName` 关联；
- 产品维度使用生产计划快照 `ProductID/ProductName`，避免分析页面直接复制产品档案逻辑。

接口会在 `dataQuality` 中返回：

- `qualityScrapRecordCount`：范围内处置方式为 `SCRAP` 的品质异常记录数；
- `missingQuantityRecords`：处置方式为 `SCRAP` 但缺少有效报废数量的记录数；
- `missingOccurrenceTimestampRecords`：缺少明确报废发生时间的记录数；
- `unlinkedQualityRecords`：无法关联到生产计划、订单、产品或批次的品质异常记录数；
- `missingCompletionTimestampRecords`：已完成但缺少完工时间的生产任务数；
- `unlinkedProductionOrderRecords`：缺少销售订单关联的生产计划数。
- `notes` 使用稳定的缺口代码，由前端按当前语言显示，不直接返回界面文案。

当前 `summary.scrapQuantity` 会汇总契约完整的品质报废事实；若范围内存在缺少数量或生产关联的记录，则仍返回 `null` 并通过 `dataQuality` 明确提示，避免部分数据被误认为完整数据。`summary.qualifiedQuantity` 已接入质量批次数量结算事实，但只在范围内所有相关批次都有有效结算记录时返回；存在缺失时仍返回 `null` 并保留 `QUALITY_QUALIFIED_QUANTITY_MISSING`。`summary.scrapRate` 和 `summary.yieldRate` 仍为 `null`，因为四类数量的统一覆盖、单位换算和分母口径尚未完成。`dataQuality.isComplete` 在统一口径完成前仍为 `false`。

### 6.1 月产能明细钻取契约

明细钻取是同一份生产计划/生产任务事实的只读投影，不重新计算一套统计口径，也不在浏览器中拼接生产、销售和品质列表。

请求：

```text
GET /api/v1/business-analysis/production-capacity/drilldown
```

除原有日期、客户、产品、状态和取消计划筛选外，必须提供：

```text
dimension=product|customer
value=<product-id|customer-id>
```

`value=__unlinked__` 用于查看没有产品或客户关联的计划。响应返回当前筛选条件、钻取维度和值、命中的生产计划，以及每个计划下的生产任务、批次、工序、状态、目标量、实际量、开始时间和完工时间。

计划量仍只按 `StartDate`（为空时回退 `CreatedAt`）归属范围；完工量仍只统计 `Status = DONE`、有 `CompletedAt` 且 `ActualQty >= 0` 的任务，并按 `CompletedAt` 归属范围。钻取动作写入 `business-analysis-query` 审计，动作类型为 `Drilldown`，同时记录维度和值。

## 11. 验收标准

经营分析域正式接入前，必须满足：

- 生产管理页面仍只负责计划和执行；
- 品质管理仍是报废事实的唯一维护入口；
- 分析页面不复制领域 CRUD；
- 同一筛选条件下，页面所有指标来自同一个后端分析响应；
- 报废数量有明确数量字段和单位；
- 无法关联的品质记录会被明确提示；
- 月份筛选不会退化为“今日完成量”；
- 首页不承载复杂分析表格；
- 新路由不依赖兼容跳转；
- 权限、审计和导出边界已测试。

> **结论**：经营分析是一个独立的跨域只读分析域。生产、销售、品质分别保留事实所有权，经营分析统一消费这些事实并提供决策视图。月产能分析作为第一张报表落地，但必须先完成报废数量和关联链路的契约确认。
