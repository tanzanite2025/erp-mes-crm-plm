## 2. 当前系统现状与断层分析

### 2.1 已具备能力（现状）

系统已具备基础“进销存”能力：

1. 采购/销售主单与明细可维护；
2. 入库/出库/调拨有库存数量联动；
3. 审批具备“配置 + 申请 + 授权码核销”的动作保护机制；
4. 财务模块有币种/账期/税率等主数据能力。

### 2.2 核心断层（根因）

1. **有实物流，无价值流**
   - 库存模型无均价字段；
   - 入库时不重算成本；
   - 出库时不快照 COGS。

2. **有业务单据，无统一凭证层**
   - 采购/销售/库存动作未生成标准化 Financial Voucher；
   - 财务与业务无法形成可追溯、可核销的一致账务链路。

3. **有审批拦截，无流程引擎**
   - 当前审批偏“动作级授权”，不具备“模板-实例-任务”的可编排能力；
   - 难以承载金额阶梯、条件分支、并行会签等后续需求。

4. **有收付款记录潜力，无标准核销模型**
   - 缺少面向 AP/AR 的多对多 ClearingEntry；
   - 无法稳定支持“单单匹配 + 余额往来”混合场景。

## 3. 已确认核心设计决策（Final Decisions）

### 3.1 成本核算：移动平均法（Moving Average）

每次入库时自动更新均价：

> 新均价 = (当前库存金额 + 本次入库金额) / (当前库存数量 + 本次入库数量)

- `Inventory` 新增 `AverageUnitCost`
- `ShipmentRecord` 出库时快照成本到 `COGS`

### 3.2 审批架构：轻量 BPM（可升级）

采用三层结构：

- `WorkflowDefinition`（定义）
- `WorkflowInstance`（实例）
- `WorkflowTask`（任务）

初期实现顺序流；模型预留并行、分支、条件路由字段，支持未来平滑升级至 BPMN 化。

### 3.3 财务核销：混合核销模型（Realistic Reconciliation）

并存两类核销方式：

1. 单单匹配（Invoice ↔ Payment）
2. 余额往来（按客户/供应商往来余额滚动抵扣）

统一通过：

- `FinancialVoucher` 记录业务债权债务
- `ClearingEntry` 记录核销明细（多对多）

### 3.4 BPM 引擎挂载模式（Workflow Attachment Pattern）

为避免审批规则散落在业务模型中，采用“业务单据挂载流程实例”的统一模式：

1. 每个需要审批的业务单据（如 PO/SO/发票）持有 `WorkflowInstanceID`；
2. 业务单据仅维护自身业务字段，不内嵌审批流转规则；
3. 单据状态流转（`Draft -> Pending -> Approved`）统一由 `WorkflowService` 托管；
4. 复杂策略（三级审批、金额阈值加签）通过流程 JSON 定义调整，不改 `trading.go` 业务模型。

### 3.5 移动平均法实现硬约束（Fail Loudly）

移动平均法的计算必须原子化且可审计，避免“静默错误”：

1. `Inventory` 增加价值字段：
   - `TotalValue`（本位币总价值）
   - `AverageUnitCost`（平均单价）
2. 入库重算公式：
   - `新总价值 = 旧库存量 * 旧平均单价 + 本次入库量 * 本次单价`
   - `新平均单价 = 新总价值 / (旧库存量 + 本次入库量)`
3. 零分母硬保护：
   - 当 `(旧库存量 + 本次入库量) == 0` 时，必须抛出 `[CRITICAL_LOGIC_ERROR]` 并回滚事务。

### 3.6 核销逻辑：最贴合现实的混合核销

核销同时支持两类现实场景：

1. **单单核销（Specific Matching）**：指定“哪张发票对应哪笔货款”；
2. **余额核销（Balance Clearing）**：到款后按规则（例如最老欠款优先）自动或半自动分配。

核心落地为 `ClearingEntry` 核销项表，基础字段：

- `VoucherID`（哪个债）
- `PaymentID`（哪个钱）
- `AllocatedAmount`（本次核销金额）

该模型天然支持：分摊、多对多、部分结清、预付款抵扣与折让扩展。

## 4. 架构总览（摘要）

为减少重复维护，本节仅保留跨专题统一口径：

1. **模型抽象口径**：
   - 业务主单承载业务事实；
   - `FinancialVoucher` 承载财务债权债务；
   - `ClearingEntry` 承载核销分配；
   - `CurrencyRateSnapshot` 承载汇率发生点快照。
2. **流程口径**：
   - 审批状态由 `WorkflowService` 托管，不在业务 Handler 中硬编码流转。
3. **成本口径**：
   - 库存同时管理数量与价值，移动平均法为默认成本模型。

## 5. 分阶段实施规划（总览）

1. **第一阶段：基座补强**
   - 补齐模型字段、事务边界与凭证映射入口。
2. **第二阶段：闭环落地**
   - 完成移动平均、工作流托管、混合核销主链路。
3. **第三阶段：可视化与审计增强**
   - 提升核销可视化、异常提示与审计追溯体验。

---

## 6. 验证与治理（总览）

1. **端到端链路**：询价 → 订单 → 入库重算均价 → 出库成本快照 → 生成凭证 → 核销。
2. **一致性校验**：库存价值、往来余额、汇率快照三类一致性。
3. **Fail Loudly 防线**：
   - 0 分母、越界核销、未托管审批三类场景必须显式失败并可审计。

---

## 7. 风险控制（总览）

1. 并发竞争：通过事务 + 行锁 + 幂等键治理。
2. 历史补录：已过账期间禁止回写历史 COGS，差异走调整凭证。
3. 错配核销：主体、币种、余额三重校验。
4. 流程绕过：未通过工作流实例不得进入 `Approved`。

---

## 8. 结论

本方案将系统从“进销存操作系统”升级为“业务-财务一致的闭环系统”：

- 成本可解释（移动平均 + COGS 快照）
- 流程可扩展（轻量 BPM，可升级）
- 财务可核销（Voucher + Clearing 混合模型）
- 架构可抽象（Agnostic 模式，支持未来业务扩展）

该方案与工业场景匹配度高，且具备可分阶段落地与可审计追踪能力。
