## 2. 当前系统现状与断层分析

### 2.1 已具备能力（现状）

系统已具备基础“进销存”能力：

1. 采购/销售主单与明细可维护；
2. 入库/出库/调拨有库存数量联动（仅指库存域真实出入库；车型匹配与装车模拟不在此闭环中）；
3. 审批以 `approval_requests` 保存真实申请；部分通用动作使用授权码验证，品质标准通过当前申请与审批决定事务回写业务，不以授权码作为统一完成条件；
4. 财务模块有币种/账期/税率等主数据能力。

### 2.2 核心断层（根因）

1. **有实物流，无价值流**
   - 库存模型无均价字段；
   - 入库时不重算成本；
   - 出库时不快照 COGS。

2. **有业务单据，无统一凭证层**
   - 采购/销售/库存动作未生成标准化 Financial Voucher；
   - 财务与业务无法形成可追溯、可核销的一致账务链路。

3. **审批扩展范围需由实际业务决定**
   - 当前审批服务支持一级/二级审批，并非任意层级或 BPMN 引擎；
   - 金额阶梯、条件分支和并行会签尚不能作为已实现能力，也不是收件箱建设必须附带的新引擎需求。

4. **有收付款记录潜力，无标准核销模型**
   - 缺少面向 AP/AR 的多对多 ClearingEntry；
   - 无法稳定支持“单单匹配 + 余额往来”混合场景。

## 3. 已确认核心设计决策（Final Decisions）

### 3.1 成本核算：移动平均法（Moving Average）

每次入库时自动更新均价：

> 新均价 = (当前库存金额 + 本次入库金额) / (当前库存数量 + 本次入库数量)

- `Inventory` 新增 `AverageUnitCost`
- `ShipmentRecord` 出库时快照成本到 `COGS`

### 3.2 审批架构：沿用真实审批申请

当前事实由 `server/models/approval.go`、`server/services/approval_service.go` 和公共审批接口维护，业务事务按自身契约创建、关联和回写审批结果。

旧 `WorkflowDefinition / WorkflowInstance / WorkflowTask` 表及销售、采购的流程实例字段已由数据库启动清理逻辑移除。原“采用三层 BPM”的描述不再作为已确认方向；后续若出现复杂审批需求，应专项设计，不重建平行状态机。

### 3.3 财务核销：混合核销模型（Realistic Reconciliation）

并存两类核销方式：

1. 单单匹配（Invoice ↔ Payment）
2. 余额往来（按客户/供应商往来余额滚动抵扣）

统一通过：

- `FinancialVoucher` 记录业务债权债务
- `ClearingEntry` 记录核销明细（多对多）

### 3.4 审批与业务单据关联边界

审批与业务状态必须由真实后端事务维护：

1. 当前品质标准明确关联本轮 `approval_request_id`，提审、申请创建和关联在同一事务提交；不能据此声称全部单据已完成同样接入；
2. 通用审批服务负责节点权限和决定，业务服务负责合法状态变化及相应业务回写；
3. 消息中心引用真实申请提供提醒，已读或归档不推进单据审批；
4. 收件箱统一方案复用当前审批事实，不附带任意三级审批、会签或流程 JSON 能力承诺。

### 3.5 移动平均法实现硬约束（Fail Loudly）

移动平均法的计算必须原子化且可审计，避免“静默错误”：

1. `Inventory` 增加价值字段：
   - `TotalValue`（本位币总价值）
   - `AverageUnitCost`（平均单价）
2. 入库重算公式：
   - `新总价值 = 旧库存量 * 旧平均单价 + 本次入库量 * 本次单价`
   - `新平均单价 = 新总价值 / (旧库存量 + 本次入库量)`
3. 零分母硬保护：
   - 当 `(旧库存量 + 本次入库量) == 0` 时，必须抛出 `[CRITICAL_LOGIC_ERROR]` 并回滚事务。

### 3.6 核销逻辑：最贴合现实的混合核销

核销同时支持两类现实场景：

1. **单单核销（Specific Matching）**：指定“哪张发票对应哪笔货款”；
2. **余额核销（Balance Clearing）**：到款后按规则（例如最老欠款优先）自动或半自动分配。

核心落地为 `ClearingEntry` 核销项表，基础字段：

- `VoucherID`（哪个债）
- `PaymentID`（哪个钱）
- `AllocatedAmount`（本次核销金额）

该模型天然支持：分摊、多对多、部分结清、预付款抵扣与折让扩展。

## 4. 架构总览（摘要）

为减少重复维护，本节仅保留跨专题统一口径：

1. **模型抽象口径**：
   - 业务主单承载业务事实；
   - `FinancialVoucher` 承载财务债权债务；
   - `ClearingEntry` 承载核销分配；
   - `CurrencyRateSnapshot` 承载汇率发生点快照。
2. **流程口径**：
   - 审批决定由当前审批服务校验，业务状态由相应后端事务维护；不再依赖已移除的 `WorkflowService`。
3. **成本口径**：
   - 库存同时管理数量与价值，移动平均法为默认成本模型。

## 5. 分阶段实施规划（总览）

1. **第一阶段：基座补强**
   - 补齐模型字段、事务边界与凭证映射入口。
2. **第二阶段：闭环落地**
   - 按各专题实际状态推进移动平均、审批业务关联、混合核销主链路；不按旧 BPM 方案重复建设。
3. **第三阶段：可视化与审计增强**
   - 提升核销可视化、异常提示与审计追溯体验。

---

## 6. 验证与治理（总览）

1. **端到端链路**：询价 → 订单 → 入库重算均价 → 出库成本快照 → 生成凭证 → 核销。
   - 其中“出库成本快照”只对应真实库存出库；`/logistics-config/vehicle-loading` 与 `/shipping-management/vehicle-match` 只产出模拟推荐，不进入财务过账。
2. **一致性校验**：库存价值、往来余额、汇率快照三类一致性。
3. **Fail Loudly 防线**：
   - 0 分母、越界核销，以及应审批动作缺少有效审批依据的场景必须显式失败并可审计。

---

## 7. 风险控制（总览）

1. 并发竞争：通过事务 + 行锁 + 幂等键治理。
2. 历史补录：已过账期间禁止回写历史 COGS，差异走调整凭证。
3. 错配核销：主体、币种、余额三重校验。
4. 流程绕过：应审批动作必须校验实际申请、当前审批人和有效决定，不能靠客户端改状态或消息已读绕过。

---

## 8. 结论

本方案将系统从“进销存操作系统”升级为“业务-财务一致的闭环系统”：

- 成本可解释（移动平均 + COGS 快照）
- 流程可扩展（轻量 BPM，可升级）
- 财务可核销（Voucher + Clearing 混合模型）
- 架构可抽象（Agnostic 模式，支持未来业务扩展）

该方案与工业场景匹配度高，且具备可分阶段落地与可审计追踪能力。
