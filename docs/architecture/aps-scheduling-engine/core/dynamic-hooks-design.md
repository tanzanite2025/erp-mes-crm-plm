# APS 排产引擎 - 动态排程钩子设计说明

## 1. 目标

本文件专门说明动态排程引擎的“钩子”机制，解决以下问题：

- 哪些业务对象可以挂钩
- 钩子触发什么事件
- 事件如何影响排程
- 哪些事件适合局部修正，哪些事件需要全局重排

这里的“钩子”不是某一个单点业务功能，而是指：

> 任何会影响资源可用性、工序可执行性、时间窗有效性、产能边界的业务状态变化，都应能作为排程引擎的输入。

---

## 2. 可以挂钩的对象

### 2.1 模具 / 工装 / 夹具

适合挂钩的状态：

- 正常
- 维修中
- 已报废
- 待校准
- 锁定
- 可用

影响：

- 某些工序无法继续
- 某些订单需要延后
- 某些产线窗口失效

---

### 2.2 设备 / 机器

适合挂钩的状态：

- 开机
- 停机
- 故障
- 维修中
- 恢复
- 降速运行

影响：

- 产能变化
- 时间窗变化
- 任务暂停或延后

---

### 2.3 人员可用性

适合挂钩的状态：

- 到岗
- 离岗
- 请假
- 休息日上班
- 临时可用

影响：

- 可排资源数量变化
- 班次可用性变化
- 产线实际产能变化

---

### 2.4 产线 / 生产结构节点

适合挂钩的状态：

- 可用
- 停线
- 维护
- 切线中
- 恢复

影响：

- 整条线或对应 L2/L3 节点的计划都可能受影响
- 可能触发大范围局部重排或全局重排

---

### 2.5 物料 / 库存

适合挂钩的状态：

- 齐套
- 缺料
- 到料
- 冻结
- 释放

影响：

- 某些工序不能开工
- 某些订单必须等待
- 可能只需要局部修正

---

### 2.6 条码 / 到岗 / 签到记录

适合挂钩的状态：

- 刷卡到岗
- 休息日到岗
- 异常签到
- 签退

影响：

- 产能变化
- 休息日临时可排
- 需要调整当天可用工时

---

### 2.7 订单 / 工序 / 工艺路线

适合挂钩的状态：

- 新增
- 变更
- 取消
- 加急
- 拆单
- 并单

影响：

- 排序变化
- 任务集合变化
- 可能触发局部或全局重排

---

## 3. 钩子触发什么事件

### 3.1 统一事件模型

动态钩子触发后，应转换成统一的排程事件：

```go
type ScheduleEvent struct {
    ID         string
    Type       string
    Source     string
    TargetID   string
    OccurredAt time.Time
    Payload    map[string]any
}
```

---

### 3.2 事件分类

#### 1. 资源状态事件

示例：

- `mold.status.changed`
- `machine.status.changed`
- `line.status.changed`
- `resource.locked`
- `resource.released`

用途：

- 更新资源可用性
- 冻结或释放相关任务

---

#### 2. 产能变化事件

示例：

- `attendance.checked-in`
- `attendance.checked-out`
- `shift.capacity.changed`
- `holiday.overtime.started`

用途：

- 增加或减少某天 / 某班次的可用产能
- 影响可排时间窗

---

#### 3. 物料状态事件

示例：

- `material.shortage.detected`
- `material.arrived`
- `material.released`

用途：

- 决定某工序是否可继续排
- 决定任务是否需要等待

---

#### 4. 订单变化事件

示例：

- `order.created`
- `order.updated`
- `order.cancelled`
- `order.urgent`

用途：

- 改变任务优先级
- 改变待排任务集合

---

#### 5. 工艺变化事件

示例：

- `route.changed`
- `process.changed`
- `split.required`

用途：

- 改变任务工序结构
- 改变任务之间的依赖关系

---

## 4. 事件如何影响排程

### 4.1 影响排程的基本维度

任何事件最终都会影响以下一种或多种维度：

1. **任务集合**
   - 任务新增、删除、拆分、合并

2. **资源集合**
   - 资源可用、不可用、锁定、释放

3. **时间窗集合**
   - 某天可排、不可排、部分可排

4. **优先级集合**
   - 紧急单插入、普通单延后

5. **冻结区集合**
   - 已执行区不动
   - 可重排区重新计算

---

### 4.2 影响路径

事件进入后，建议按这个顺序处理：

1. 识别事件类型
2. 找到受影响对象
3. 判断对象是否在冻结区内
4. 评估影响范围
5. 决定局部修正或全局重排
6. 生成新版本
7. 记录差异和原因

---

### 4.3 影响示例：模具坏了

如果模具状态从“正常”变成“维修中”：

- 相关工序不可继续
- 使用该模具的任务被冻结
- 若影响范围较小，只对受影响任务做局部修正
- 若影响了关键瓶颈资源，触发全局重排

---

### 4.4 影响示例：休息日有人上班

如果条码记录显示休息日有人到岗：

- 当天可用产能提升
- 可排时间窗增加
- 原本延期的任务可能提前
- 通常先做局部修正，不一定需要全局重排

---

## 5. 哪些是局部修正，哪些是全局重排

### 5.1 局部修正

适用条件：

- 影响范围小
- 只影响某条线、某天、某个班次
- 任务未大面积连锁变化
- 订单依赖关系未整体改变

常见场景：

- 模具短时不可用，但只影响少量任务
- 某批人员临时可用
- 某条线当天加班
- 物料临时到料
- 单个设备短时恢复

结果：

- 只重新计算受影响任务
- 只更新局部时间窗
- 保留其他计划不变

---

### 5.2 全局重排

适用条件：

- 影响范围大
- 关键瓶颈资源变化
- 订单优先级大幅变化
- 工艺路线变化
- 局部修正无法得到可行解

常见场景：

- 核心模具报废
- 主设备长时间停机
- 产线整体停线
- 大量订单被插入
- 工艺路线被重新定义

结果：

- 重新计算更大范围的排程
- 可能重算整条线、整天、整批订单
- 生成新的计划版本

---

### 5.3 判断规则建议

可以用下面的判断逻辑：

1. **是否影响冻结区**
   - 影响已执行区：只能记录差异，不能回写
   - 影响可重排区：允许修正

2. **是否影响关键瓶颈资源**
   - 影响关键瓶颈：倾向全局重排
   - 影响非关键资源：倾向局部修正

3. **是否改变任务依赖结构**
   - 改变工艺路线 / 拆单 / 并单：倾向全局重排

4. **局部重排是否能找到可行解**
   - 找得到：局部修正
   - 找不到：升级全局重排

---

## 6. 建议的钩子接口

### 6.1 钩子注册

```go
type ScheduleHook interface {
    Supports(targetType string) bool
    BuildEvent(targetID string, payload map[string]any) ScheduleEvent
}
```

---

### 6.2 影响分析器

```go
type ImpactAnalyzer interface {
    Analyze(event ScheduleEvent, currentPlan *SchedulePlan) ImpactScope
}
```

---

### 6.3 重排决策器

```go
type ReplanDecider interface {
    Decide(scope ImpactScope) ReplanMode
}
```

其中：

- `ReplanModeLocal`
- `ReplanModeGlobal`
- `ReplanModeIgnore`

---

## 7. 落地建议

### 第一层：先允许挂钩

先把模具、设备、人员、物料、产线这些对象都能发事件。

### 第二层：再做影响分析

判断每个事件影响哪些任务、资源和时间窗。

### 第三层：再做重排策略

根据影响范围决定局部修正还是全局重排。

### 第四层：再做审计

所有事件和重排必须可回放、可追踪、可解释。

---

## 8. 结论

动态排程钩子的关键不是某一个具体对象，而是建立一套统一机制：

- 业务对象状态变化 → 事件
- 事件 → 影响分析
- 影响分析 → 局部修正 / 全局重排

模具状态只是一个典型例子，真正要做的是让排程引擎支持所有关键资源的状态变化。
