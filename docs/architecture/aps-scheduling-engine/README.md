# APS 排产引擎总方案

## 1. 目标

本目录用于专门沉淀“订单到生产排产”的后端引擎设计。该引擎将承担：

- 订单下达后的自动排产
- 产线/工序/资源/班次/日历约束计算
- 休息日、节假日、停线日的排程判断
- 条形码、签到、到岗等动态事件触发的排产修正
- 排产版本管理、重算、回滚与审计

该能力与现有页面展示解耦，属于独立的后端业务引擎，不应继续拆散在前端模块或零散服务中。

## 2. 设计原则

1. **真实约束优先**
   - 排产必须以真实生产约束为准，不允许只靠静态假数据。

2. **静态计划 + 动态修正**
   - 初始排产是基于订单与资源的静态计划。
   - 后续通过事件驱动进行局部修正或重排。

3. **日历是第一类对象**
   - 工作日、休息日、节假日、临时加班、停线日都必须可建模。

4. **事件可追溯**
   - 条码刷卡、到岗、设备开机、缺料、停机等都应进入事件流，而不是直接改结果。

5. **排产可版本化**
   - 每次重算都要留版本、差异、触发原因和生效范围。

## 3. 核心业务问题

### 3.1 订单如何进入排产

订单进入后，需要转换成可排产对象，通常包含：

- 订单头 / 订单行
- 交期
- 优先级
- 产线或工艺路线
- 工序耗时
- 所需资源
- 是否可拆单 / 并单 / 插单

### 3.2 休息日如何处理

系统需要识别：

- 正常工作日
- 法定节假日
- 产线休息日
- 临时停机日
- 节假日加班窗口

### 3.3 条形码如何影响排产

如果休息日实际有人上班，且有条形码/签到/到岗记录，系统需要：

- 识别当天实际可用产能变化
- 将原本“不可排”或“低可用”状态调整为可排
- 触发局部排产修正
- 保留审计记录

## 5. 建议的系统边界

该引擎不应直接承担以下职责：

- 不负责前端看板展示细节
- 不负责 `/personnel/line` 页面逻辑
- 不负责普通用户权限模型
- 不直接混入采购、销售、库存的通用 CRUD

它只专注于：

- 生产排程决策
- 约束求解
- 事件驱动修正
- 排产版本管理

## 6. 近期优先事项

如果要正式开始设计，建议按这个顺序推进：

1. 定义数据模型
2. 定义排产规则优先级
3. 定义日历与休息日策略
4. 定义条码事件如何修正产能
5. 定义重排和冻结机制
6. 再进入后端实现
