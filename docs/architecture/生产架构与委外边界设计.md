## 1. 决策摘要

### 1.1 产线管理 TAB 的最终归属

`产线管理` 与 `产线脑图` 当前都围绕同一份 `/production/lines` 数据工作，并且都能修改产线层级。两者长期并存会造成：

- 用户不知道应该在哪个页面维护产线；
- 同一条产线出现两套编辑入口；
- 权限、搜索、最近访问和路由目录需要同时维护；
- 后续委外、工序转移、产能分析无法确定哪个页面是产线结构的权威来源。

最终决策：

```text
产线脑图 = 产线主数据 + 工段层级 + 工序定义的唯一入口
```

独立的 `产线管理` TAB 应删除，而不是保留空壳、跳转页或兼容入口。

### 1.2 删除前的必要前置条件与当前状态

迁移前，脑图缺少以下产线基础操作；这些能力已在本次迁移中补齐：

- 新增产线；
- 编辑产线名称、编码、描述；
- 启用/停用产线；
- 删除产线；
- 产线级操作菜单；
- 拓扑模板的应用/保存入口。

这些前置条件已在 `产线脑图` 迁移中完成，旧 `line` 路由也已删除。实施顺序记录如下（均已完成）：

1. 先将产线基础操作迁入脑图工具栏或“当前产线操作”菜单；
2. 补齐脑图对应的权限状态、确认弹窗和空数据状态；
3. 验证脑图成为完整的产线管理入口；
4. 删除 `line` TAB、旧路由、搜索项、权限目录项和旧菜单引用；
5. 重新生成路由目录与权限索引；
6. 运行前端构建、后端测试和路由/权限一致性检查；
7. 最后再进入委外功能设计与实现。

当前进度：步骤 1 到 6 已完成并提交，生产路线、条码状态、工序执行基础骨架、委外单位档案和委外任务首期已落地；委外专项设计已迁入 `docs/architecture/生产委外执行链路设计.md`。下一步不再补一个孤立委外表单，而是继续补扫码发出、扫码回收和回收检验。委外不另建单位与工序的能力映射，产品当前工序只认一维码状态中的 `routeStepId`。

## 4. 重复职责与长期风险

### 4.1 重复职责

旧 `line-mgmt` 和 `line-mindmap` 都：

- 读取 `/production/lines`；
- 展示产线与层级；
- 修改产线拓扑；
- 触发版本更新；
- 受生产域权限保护。

差异仅在呈现方式和脑图额外的 L3 绑定操作。继续保留两个页面会让同一份拓扑出现“双写入口”。

### 4.2 当前保存模型的风险

`SaveProductionLine` 会按整棵层级树保存，并删除不再提交的关联节点。该模式可以保证一棵树的整体一致性，但要求：

- 所有写入都携带最新 `version`；
- 任何页面都不能只提交局部旧快照；
- 脑图和未来委外页面不能直接修改产线拓扑；
- 发生 409 时必须让用户重新读取，而不是静默覆盖。

因此脑图成为唯一拓扑写入口后，版本冲突更容易定位，长期稳定性更高。

### 4.3 权限风险

当前前端路由、搜索和权限目录仍显式包含：

- `src/features/authz/data/authenticated-route-catalog.ts`
- `src/features/authz/data/route-permission-labels.ts`
- `src/components/layout/data/search-data.ts`
- `src/features/production-architecture/tab-config.ts`
- `src/routes/_authenticated/production-architecture/line.tsx`

删除 TAB 时必须一起清理，否则会出现“页面没有入口但权限/搜索仍可进入”的幽灵路由。

后端的权限边界仍应保留：

- 读取产线：生产配置菜单权限；
- 修改拓扑：`action_production_line_update`；
- 新增/删除产线：管理员权限；
- 拓扑敏感操作：`topology_auth_password` 二次授权。

## 5. 产线唯一入口的目标结构

```text
生产管理
└─ 生产协同
   └─ 生产架构
      ├─ 产线脑图（唯一产线管理入口）
      │  ├─ 产线选择与搜索
      │  ├─ 新增产线
      │  ├─ 编辑产线资料
      │  ├─ 启用 / 停用
      │  ├─ 删除产线
      │  ├─ 新增 / 编辑 L1、L2、L3 节点
      │  ├─ L3 库与节点绑定
      │  └─ 拓扑模板应用 / 保存
      └─ 拓扑模板
```

脑图工具栏建议分为三组，避免按钮继续堆叠：

1. **产线选择**：搜索、切换当前产线；
2. **产线操作**：新增、编辑、启停、删除、模板；
3. **结构操作**：新建 L1/L2/L3 节点、编辑当前节点。

产线资料弹窗与节点编辑弹窗必须区分：

- 产线资料：名称、编码、描述、状态；
- 节点编辑：L1/L2/L3 节点名称、节点说明和 L3 绑定。

## 7. 委外/外协的长期领域边界

产线入口收敛后，再设计委外。委外不是采购订单的附属页面，也不是供应商资料的另一个别名；它是生产执行在某个工序节点上的外部执行方式。

### 7.1 领域归属

```text
生产管理
├─ 计划中心
├─ 生产协同
│  └─ 生产架构 / 产线脑图
└─ 委外管理
   ├─ 委外基础
   │  ├─ 委外单位
   │  └─ 委外协议/价格
   └─ 委外执行
      ├─ 委外任务
      ├─ 发出
      ├─ 在外
      ├─ 回收
      └─ 委外检验
```

委外属于生产管理域。采购域可以维护结算、付款和供应商合作信息，但不能拥有“某个产品当前处于哪个生产工序”的事实。

### 7.2 产品、一维码、账号权限与产线必须分开

| 对象 | 原因 |
| --- | --- |
| `Product` | 产品主数据和产品规则来源，可用于打印生成一维码，但不保存某个一维码当前在哪道工序 |
| 产品一维码 | 由产品/订单打印发号产生，可反查产品；生产执行把当前工序状态绑定到一维码 |
| `ProcessStep` | 工序定义，包含具体操作、执行方式、质量关卡和转移要求，不承载人员授权 |
| 账号权限 / 命令权限 | 决定某个账号是否能打开页面、点击按钮或执行扫码命令，属于权限系统 |
| `Position` / `EmployeeAssignment` | 组织人事资料，可用于人员档案展示，不参与生产扫码或工序执行授权 |
| `ProductionLine` / `LineSegment` | 产线和工段主数据，只描述生产结构，不保存操作人状态 |
| `Supplier` | 供应商适合采购合作方，不能自动代表生产执行事实 |
| `EquipmentPartner` | 设备/工装合作方与生产加工委外不是同一事实 |
| 裁纱卷材绑定 | 裁纱与卷材追溯是独立模块，不能成为后续生产或委外的硬前置 |

一维码的最短执行链路固定为：

```text
产品/订单行
  → 打印生成一维码
  → 扫码反查产品
  → 读取一维码当前工序状态
  → 扫码账号
  → 页面/命令/动作权限校验
  → 工序执行或转移事件
```

这条链路不要求同步加载完整生产计划、库存、卷材或委外数据。其他领域只通过明确 ID 或产品一维码关联，避免一次扫码触发大范围数据串联。

绑定错误时，必须能从一维码直接查到：

- 对应的产品；
- 当前工序；
- 最近一次状态事件；
- 操作账号；
- 关联路线版本。

当前已落地基础状态链：

```text
product_barcode_states
  └─ product_barcode_state_events
```

该链路只以一维码为锚点保存当前工序状态和事件历史，产品 ID、路线 ID、路线步骤 ID 均为可选稳定引用。它不要求先存在卷材绑定，也不要求加载完整生产计划，后续扫码执行、转移和委外只需要继续写入这条状态链。

当前也已落地 `production_execution_lots`，用于把产品码可选归入生产计划、任务和批次。它服务于批量追踪和后续产能分析，不是扫码执行或委外流转的前置条件。

当前已落地 `production_operation_executions`，用于记录某个产品码在某个工序上的开始、完成、暂停或返工动作。该服务只校验工序、路线、批次等生产事实；是否允许调用扫码、按钮或接口，由账号/人员权限体系在入口侧处理。写入成功后会同步写入一维码状态事件。

当前已落地统一扫码命令入口：

```text
POST /production/scan-commands/execute
```

该入口是 Web、PDA、USB 扫码的统一后端命令层，复用 `action_production_issuance_execute` 动作权限，不从工序或人员档案推导授权。它会从一维码当前状态、请求参数和路线步骤解析当前执行上下文，完成后按路线 `sequence` 推进下一步骤。

当前已落地转移事件基础表：

```text
product_barcode_transfer_events
```

它用于记录路线推进和可选持有方变化，不等于委外发出/回收业务状态机。委外发出、回收、在外和回收待检仍需要后续独立实现。

### 7.3 建议的核心实体

```text
ProductionRoute
  └─ ProductionRouteStep

ProductionLine
  └─ LineSegment（工段）
      └─ ProcessStep（工序）

ProductBarcodeState
  ├─ productBarcode
  ├─ productId
  ├─ currentProcessStepId
  └─ status

ProductBarcodeStateEvent
  ├─ productBarcode
  ├─ fromProcessStepId
  ├─ toProcessStepId
  ├─ operatorAccount
  └─ occurredAt

ProductionExecutionLot
  ├─ productBarcode
  ├─ planId / taskId
  └─ optional batch reference

ProductionOperationExecution
  ├─ productBarcode
  ├─ routeStep
  ├─ processStep
  ├─ startedAt / completedAt
  └─ result

OutsourcePartner

OutsourceOrder
  └─ OutsourceOrderLine
      ├─ productBarcode
      ├─ routeStep
      ├─ quantity
      └─ requiredProcessStep

OutsourceTransfer
  ├─ sentAt
  ├─ returnedAt
  ├─ quantity
  └─ custody/location

OutsourceInspection
  ├─ result
  ├─ acceptedQuantity
  ├─ rejectedQuantity
  └─ disposition
```

当前已经落地 `OutsourceOrder` / `OutsourceOrderLine` 首期骨架。它支持从销售订单或生产计划创建委外任务，销售订单和生产计划只作为来源快照；委外任务自己保存委外单位、数量、来源产品快照、计划发出/返回日期和状态，创建时不手工绑定 L3。因此“销售订单 500 件，本厂做不过来，直接开始委外”目前已有基础登记入口。

委外任务行不再手工选择 L3。L3 属于产线流程定义；一个产品当前处于哪个工序，应由一维码加工状态表达。后续扫码发出/回收会读取一维码当前工序状态并写入转移事件，而不是在委外页反向修改产线脑图或工序库。

但该首期骨架还没有形成完整流转：扫码发出、扫码回收、回收检验、质量结果驱动路线跳转仍在后续阶段。

### 7.4 状态必须拆开

委外设计不能只用一个 `status` 解决所有问题，至少要区分：

| 状态维度 | 示例 |
| --- | --- |
| 工序状态 | `NOT_STARTED`、`IN_PROGRESS`、`COMPLETED`、`HOLD` |
| 委外状态 | `DRAFT`、`RELEASED`、`SENT`、`IN_PROCESS`、`RETURNED`、`CLOSED`、`CANCELED` |
| 质量状态 | `PENDING`、`PASSED`、`FAILED`、`CONCESSION`、`REWORK` |
| 持有位置 | 本厂产线、待发区、委外单位、回收待检区、合格区、不合格区 |

“产品到了哪个工序”由一维码的 `currentProcessStepId` 和状态事件表达；“这次操作是否完成”由工序执行记录表达；“东西现在在哪里”由转移事实表达；“是否允许进入下一道工序”由工序完成和质量判定共同决定。

工序与账号权限的关系必须分开：

```text
ProcessStep
  └─ 只保存工序定义、工艺事实和路线锚点

账号
  └─ 页面权限 / 命令权限 / 动作权限
```

不允许把员工、账号或人员授权写进产线层级，也不允许通过产线节点推断操作人。组织人事域负责人员资料和组织归属；生产执行链路只记录操作账号。

### 7.5 委外执行链路

```mermaid
flowchart LR
  A["产品/订单行"] --> B["打印生成一维码"]
  B --> C["当前工序状态"]
  C --> D["扫码账号"]
  D --> E["账号权限校验"]
  E --> F{"本厂执行 or 委外执行"}
  F -->|本厂| G["工序执行记录"]
  F -->|委外| H["委外任务"]
  H --> I["发出转移"]
  I --> J["委外单位在制"]
  J --> K["回收转移"]
  K --> L["委外检验"]
  L -->|合格| M["下一路线工序"]
  L -->|不合格| N["返工/让步/报废"]
```

委外任务创建只绑定来源订单/计划、委外单位和数量；委外执行动作必须扫描产品一维码并读取其当前 `routeStepId`，不允许在任务表里手填或预选 L3。

### 7.6 一维码与裁纱边界

产品、一维码和裁纱/卷材追溯是三个独立事实：

- 产品主数据只描述产品本身；
- 一维码由产品/订单打印产生，可反查产品，并承载当前工序状态；
- 产品只要完成必要的一维码/产品绑定，就可以进入后续下单和生产流程；
- 是否绑定卷材、是否完成裁纱计算，不得成为普通生产或委外的强制阻断条件；
- 裁纱结果可作为追溯、自动切割和后续质量分析的补充事实；
- 委外系统只能引用裁纱追溯信息，不能反向要求所有产品必须先绑定卷材。

一维码绑定错误必须通过一维码、产品引用和状态事件快速发现，不能依赖卷材、库存或整张生产计划才能判断。

这是生产执行和裁纱引擎之间的硬边界，必须在后续接口契约和验收用例中明确。

## 10. 最终验收原则

### 产线架构

- 一个产线只有一个维护入口：产线脑图；
- 产线资料与产线拓扑在同一领域内，但弹窗职责分离；
- 所有写入共享同一版本、授权、审计和缓存链路；
- 删除旧路由后，搜索、权限、侧边栏和最近访问不再出现旧入口；
- 不保留兼容跳转和旧连接。

### 委外/外协

- 委外任务创建不预选 L3；发出、回收和检验必须以扫描的一维码当前状态为准；
- 工序状态、委外状态、质量状态、持有位置互不混淆；
- 产品、一维码、账号权限和产线工序互不混淆；
- 委外单位不是简单复制采购供应商；
- 委外回收必须经过质量判定才能进入下一工序；
- 裁纱/卷材追溯不会阻断未绑定产品进入正常生产链路；
- 生产、采购、品质、仓储和裁纱分别拥有自己的事实所有权。

> 结论：产线唯一入口迁移已完成。系统结构固定为 L1 → L2 → L3；统一扫码命令入口、账号动作权限落点、路线推进、转移事件基础、委外单位和委外任务首期已落地。下一步继续补发出/回收/检验状态机，并且必须复用这条生产执行主链。
