# 生产拓扑、路线步骤与独立工资计算边界

更新日期：2026-11-17。原文将生产作业、路线、报工及工资结算串联为一条链路，该设计错误，已撤销。财务只使用已有人员、部门和独立环节工价录入数量、计算工资，不需要生产报工、审核或收付流程。

工资唯一实施契约见 [`独立计件工资模块契约与实现边界.md`](独立计件工资模块契约与实现边界.md)。本文只保留生产模型说明及双方边界，不保留已撤销的产品路线工价配置建议。

当前路线头部按稳定 MBOM 分支身份和适用范围绑定实际存在且当前有效的分支；型号由分支带出。脑图 L1 关联产品侧模板，L2 直接选择有效 MBOM 分支，L3 是该分支独立维护的工序。路线 TAB 可直接从工序库选工序，服务端为该分支建立或复用 L3 身份并保存来源关联。路线步骤、条码状态、扫码执行和委外事实均使用 `branchOperationId`；路线位置另用 `routeStepId`。路线发布前验证有效分支、L3 和工序库来源；草稿路线不能用于扫码执行。路线按销售订单明细范围或分支默认范围匹配，详见 [`生产脑图产品BOM分支绑定与生产路线分阶段修正设计.md`](生产脑图产品BOM分支绑定与生产路线分阶段修正设计.md) 阶段 G。生产位置与 L2、工序、持有方分别建模。产品模板不筛选 L2；拓扑模板按独立快照单向复制新 L1/L2，不回写既有实际结构、不覆盖共享 L3 或路线；工资隔离契约保持不变。

## 1. 生产模型

```text
Product 产品
  -> 有效生产 MBOM 分支（产品、归属、性能版本）
    -> 分支独立工序（脑图 L3）
    -> ProductionRoute 路线
      -> ProductionRouteStep 路线步骤
        -> branchOperationId
```

脑图 L3、路线步骤、条码状态、执行记录和委外事实均使用 MBOM 分支下独立维护的分支工序身份。路线步骤 ID 仍表示有序路线位置；统一扫码命令通过它定位步骤，再取得 `branchOperationId`。旧映射路径已清理。全局 `ProcessStep` 只作为复制分支工序初始内容的来源，不是路线或执行身份。

生产计划确定本批生产的稳定 MBOM 分支并保存排产时绑定的路线修订，产品码通过执行批次关联计划。扫码读取计划固定修订，客户端不选择批次、路线或当前工序；计划已有批次或执行事实后禁止更换分支。路线按 `SalesOrderLineID` 匹配订单明细范围；没有该 ID 时使用 MBOM 分支默认路线。阶段 G 已实现该适用范围。

单作业工段可以在界面扁平展示，多作业工段需要选择具体下级作业；这些只是生产配置，与工资工价无关。

| 对象 | 文件 | 含义 |
|---|---|---|
| 产线与工段 | `server/models/production_topology.go` | 生产结构 |
| 标准作业 | `server/models/production_process.go` | 可复用生产作业 |
| 路线与步骤 | `server/models/production_route.go` | 产品执行顺序及约束 |
| 生产执行 | `server/models/production_execution.go` | 生产动作、请求回执及轮次 |

## 2. 工资模型

```text
既有人员和部门 + 独立工资环节与工价 + 财务输入数量
  -> 工资计算明细
  -> 人员、部门汇总（分币种）
```

`PieceworkPayItem` 表示独立工资环节，`PieceworkRate` 表示该环节按单位和生效日期维护的工价。计算直接读取既有人事主数据，不能引用 `ProcessStep`、`ProductionRouteStep`、产品、条码、批次、BOM 或用料分配。

不再使用 `PieceworkRecord` 模型，没有报工提交、待计价补录、结算审核、收付登记或金额调整。录错后修改输入、重新计算；无生效工价时直接报错。计算不会写入业务事实。

工价只使用 `payItemId`、`unitPrice`、`currency`、`effectiveFrom/effectiveTo`、状态和行版本，旧字段与别名不兼容。工价区间与版本属于工资维护，生产路线版本属于生产，两者不关联。

## 3. 已有生产保护与后续生产事项

常规启动不再调用破坏性拓扑清理。路线支持 `DRAFT/PUBLISHED` 业务修订：发布前重新校验分支和步骤，发布修订不能原地修改或删除；路线家族、独立业务修订号、历史快照和复制修订已实现。订单明细级路线适用范围及按 `SalesOrderLineID` 排产绑定已在阶段 G 实现。

生产 HTTP 执行和扫码要求自己的 `idempotencyKey`，回执与生产副作用同事务提交。同条码操作串行化，完工按条码、路线步骤、作业与轮次唯一；返工开启下一生产轮次。生产轮次不生成工资，生产请求不携带工资归属字段。

计划、批次产品与扫码路线之间的一致性校验已按阶段 C 实现，并通过隔离 PostgreSQL 的计划行锁交错测试。D1 已补齐分支工序停用的引用保护：已发布路线或当前/历史执行事实引用时返回业务冲突，发布与停用锁定同一工序行；名称、说明仍可独立维护。D2 已补齐 L1/L2 归属及删除一致性：L2 ID 不可跨 L1 借用或复用已删除记录，保存/删除串行锁定 L1，删除原子移除其 L2 关联，审计失败整体回滚。L1/L2 是脑图关联，停用/移除不级联改动共享分支工序、路线或执行事实。这些不是工资计算的前置条件。

## 4. 迁移与验证边界

生产回执和轮次迁移只处理生产表。工资迁移只维护独立环节和工价，不创建、迁移或推导工资报工及收付记录。业务库尚未执行本轮应用迁移。

2026-11-17，本地隔离 PostgreSQL 15 已通过生产身份迁移回滚、重复启动、L2 必填产品列、计划/批次锁定及扫码并发重放验收；实际目标部署数据库的迁移与部署后验收尚未执行。命令及边界记录于分阶段修正设计。

工资应能在没有生产表时完成财务录入与计算；生产应能在没有工资表和员工工资绑定时完成执行及扫码。这两项边界分别由测试验证，不能再恢复生产自动计件 hook。
