# 销售退货 / 销售换货执行链路设计

> 文档状态：已按当前代码核对，作为执行链路收口与剩余缺口清单<br>
> 确认日期：2026-07-28<br>
> 代码核对日期：2026-07-28<br>
> 适用范围：销售退货、销售换货、售后条码录入、仓库退回入库、换货补发、订单行级售后追踪

## 1. 结论先行

销售退货和销售换货不能只挂在销售订单头上。真正可操作的对象必须是销售订单明细行：

```text
SalesOrder
  SalesOrderLine 1  产品 A
  SalesOrderLine 2  产品 B
  SalesOrderLine 3  产品 C

退货 / 换货动作必须精确绑定到 SalesOrderLine
```

如果只记录 `salesOrderId`，一个订单里有多个产品、多行同产品或分批交付时，系统无法判断到底退的是哪一行、换的是哪一行、仓库收到的条码应该冲哪一行。后续库存、应收冲减、售后追踪都会错位。

核心决策如下：

1. 退货、换货必须以 `salesOrderLineId` 为行级锚点。
2. 产品码和条码要分清：
   - 产品码是 SKU / 型号 / 产品快照；
   - 条码 / 标签码是退回或补发实物的识别码。
3. 退货条码可以创建退货时先录入，也可以等仓库收到退货后再录入。
4. 换货既有旧货退回链路，也有新货补发链路，必须同时记录：
   - 旧货退回运单号；
   - 旧货条码 / 标签码；
   - 补发产品码；
   - 补发运单号；
   - 补发条码 / 标签码。
5. 仓库收到退货或旧货后，入库事实必须回写退货/换货状态，不能只改仓库库存。
6. “销售退货草稿 / 销售换货草稿”不应作为主页面的独立大列表。主视图应以源订单卡片为入口，在相关订单卡片或订单行里直接显示退货/换货状态列和关联单据。

## 3. 页面形态决策

### 3.1 退货页主视图

退货页展示源订单卡片，但卡片内部必须展开到行级：

```text
订单 ZP6AGS26050003
  客户 / 日期 / 状态 / 总数量

  行号  产品码  产品名称  已交付  已申请退货  已入库退货  可退数量  最新退货状态  操作
  1     A001    ...      20      5           3           15        部分入库      发起退货
  2     B002    ...      10      0           0           10        无            发起退货
```

只在退货页显示退货相关列，不污染销售订单主页面。

点击订单行或“发起退货”后进入退货操作面板，面板职责是：

1. 选择本次退货数量；
2. 可选录入退回物流单号；
3. 可选录入退回条码 / 标签码；
4. 录入退货原因、异常分类、凭证；
5. 创建真实退货单。

已经创建的退货单不放到下面独立占位区作为主入口，而是在源订单卡片的对应行下显示关联记录：

```text
行 1 关联退货：
  TH20260728001  申请 5 / 已入库 3  待补物流  查看 / 补录 / 收起
```

### 3.2 换货页主视图

换货页也以源订单卡片为入口，但显示换货相关列：

```text
订单 ZP6AGS26050003
  行号  原产品码  产品名称  已交付  已换货  可换数量  补发产品码  旧货运单  补发运单  换货状态  操作
  1     A001      ...      20      2       18        A001-R       SF...     YT...     补发中    发起换货
```

点击订单行或“发起换货”后进入换货操作面板，面板职责是：

1. 选择具体订单行；
2. 填写换货数量；
3. 录入旧货退回运单号；
4. 录入旧货条码 / 标签码；
5. 录入补发产品码；
6. 录入补发运单号；
7. 录入补发条码 / 标签码；
8. 录入换货原因、备注、凭证。

换货和退货不同：退货只处理“客户退回什么”；换货同时处理“客户退回什么”和“我们补发什么”。

### 3.3 关于草稿列表

“草稿”可以存在于弹窗或表单的本地未提交状态，但不应作为页面主视图的大列表。

建议收口为：

| 对象 | 是否需要独立主列表 | 原因 |
| --- | --- | --- |
| 销售退货单 | 不作为当前页面主入口；可作为高级查询页或筛选结果 | 退货单应直接挂回订单行上下文 |
| 销售换货单 | 不作为当前页面主入口；可作为高级查询页或筛选结果 | 换货单必须回到源订单行和补发明细 |
| 草稿 | 不建议落成主列表 | 草稿容易变成第二套业务事实，和源订单状态脱节 |

如果后续确实需要“全部退货单 / 全部换货单”查询，可以做成独立查询视图，而不是压在源订单操作页底部。

## 5. 条码和产品码绑定规则

### 5.1 退货条码录入时机

退货条码支持两种时机：

| 时机 | 场景 | 系统动作 |
| --- | --- | --- |
| 创建退货时先录入 | 客户已经提供条码、照片或面单 | 先写入 `SalesReturnLineBarcode`，状态为 `PENDING` |
| 仓库收到后录入 | 客户没有提前提供，仓库实物到达后扫码 | 仓库入库时创建或补写 `SalesReturnLineBarcode` |

两种方式最终都必须绑定到 `salesReturnLineId`，不能只挂到退货单头。

### 5.2 仓库扫码如何绑定到订单行

仓库收到退货或换货旧货时，扫码解析优先级：

1. 如果条码能反查到原发货记录或销售订单行，直接绑定对应 `salesOrderLineId`。
2. 如果条码包含产品码，只能定位到产品，系统在当前退货/换货单内筛选相同产品码的行。
3. 如果只有一条候选行，自动绑定。
4. 如果有多条候选行，必须让仓库人员选择行号，不能静默绑定。
5. 如果没有候选行，进入 `MANUAL_REVIEW`，不得更新已入库数量。

任何模糊绑定都必须显式处理，不能为了省一步把条码挂到订单头。

### 5.3 产品码和条码不能混用

产品码用于确认“是什么产品”；条码用于确认“是哪一件 / 哪一箱 / 哪个标签”。

退货：

```text
SalesReturnLine.productCodeSnapshot = 要退的产品
SalesReturnLineBarcode.normalizedCode = 退回实物条码
```

换货：

```text
SalesExchangeLine.originalProductCodeSnapshot = 客户退回的原产品
SalesExchangeLine.replacementProductCode = 我们补发的产品
SalesExchangeLineBarcode(side=OLD_ITEM) = 旧货条码
SalesExchangeLineBarcode(side=REPLACEMENT_ITEM) = 补发货条码
```

## 6. 状态流转

### 6.1 退货状态

退货状态建议拆成单头状态和行状态。

单头状态：

```text
Created
AwaitingReturn
InTransit
PartiallyReceived
Received
Closed
Canceled
```

行状态：

```text
Requested
PartiallyReceived
Received
MismatchPendingReview
Canceled
```

状态推进规则：

1. 创建退货单后进入 `Created` 或 `AwaitingReturn`。
2. 录入退回运单号后可进入 `InTransit`。
3. 仓库入库一部分后进入 `PartiallyReceived`。
4. 所有退货行 `receivedQuantity >= requestedQuantity` 后进入 `Received`。
5. 财务冲减、退款或售后关闭后进入 `Closed`。

### 6.2 换货状态

换货状态不能复用退货状态，建议：

```text
Created
AwaitingOldItem
OldItemInTransit
OldItemPartiallyReceived
OldItemReceived
ReplacementPreparing
ReplacementPartiallyShipped
ReplacementShipped
Closed
Canceled
```

换货至少有两条物流线：

| 物流线 | 字段 | 状态影响 |
| --- | --- | --- |
| 客户退回旧货 | `receivedOldItemTrackingNo` | 推进旧货在途、旧货已收 |
| 我方补发新货 | `replacementTrackingNo` | 推进补发准备、补发已发 |

旧货入库不等于换货完成。补发数量小于换货数量时应保持 `ReplacementPartiallyShipped`，只有旧货处理和补发处理都完成后，换货才能关闭。

当前代码仍用 `Draft` 表达“已创建、待旧货入库”的初始状态；旧货只收了一部分时推进到 `OldItemPartiallyReceived`，全部旧货收齐后推进到 `OldItemReceived`，仓库待入库队列会同时读取 `Draft` 和 `OldItemPartiallyReceived`。

## 7. 仓库入库与状态同步

仓库收到退货或换货旧货时，不能只写库存入库。必须生成售后入库事实并回写售后单据。

建议链路：

```text
仓库扫码收货
  解析条码 / 产品码
  定位 SalesReturnLine 或 SalesExchangeLine
  校验数量和产品是否匹配
  写入 WarehouseInboundRecord
  写入 Return/Exchange Line Barcode Binding
  更新 line.receivedQuantity
  更新单头状态
  发出 AfterSalesInboundConfirmed 事件
```

库存入库是仓库事实；退货/换货状态是售后事实。二者通过同一个事务或同一个可靠事件保持一致。

### 7.1 退货入库回写

```text
WarehouseInboundRecord
  sourceType: SALES_RETURN
  sourceId: salesReturnId
  sourceLineId: salesReturnLineId

提交后：
  SalesReturnLine.receivedQuantity += inboundQuantity
  SalesReturn.status 重新计算
  SalesOrderLine.returnedQuantity / receivedReturnQuantity 同步更新
```

### 7.2 换货旧货入库回写

```text
WarehouseInboundRecord
  sourceType: SALES_EXCHANGE_OLD_ITEM
  sourceId: salesExchangeId
  sourceLineId: salesExchangeLineId

提交后：
  SalesExchangeLine.oldItemReceivedQuantity += inboundQuantity
  SalesExchange.status 重新计算
```

### 7.3 换货补发出库回写

补发新货不应该通过退货入库逻辑处理。它应该走出库 / 发货链路：

```text
ShipmentRecord
  sourceType: SALES_EXCHANGE_REPLACEMENT
  sourceId: salesExchangeId
  sourceLineId: salesExchangeLineId
  productCode: replacementProductCode

提交后：
  SalesExchangeLine.replacementShippedQuantity += shippedQuantity
  SalesExchange.replacementTrackingNo 更新
  SalesExchange.status 重新计算
```

## 10. 不能做的短期捷径

| 捷径 | 为什么不能做 |
| --- | --- |
| 只保存 `salesOrderId` 不保存 `salesOrderLineId` | 多产品订单会无法准确退换 |
| 把条码挂到订单头 | 仓库入库后无法知道冲哪一行 |
| 用草稿列表当主视图 | 售后事实会脱离源订单上下文 |
| 退货和换货共用同一套表单 | 换货需要补发产品码、补发运单和新货条码 |
| 仓库入库只改库存不回写售后单 | 页面状态永远不同步 |
| 产品码匹配不唯一时自动绑定 | 会造成错误入库和错误售后数量 |

## 11. 最终目标

退货和换货页面最终应该让用户一眼看到：

1. 哪张订单的哪一行还能退；
2. 哪张订单的哪一行还能换；
3. 已经申请了多少；
4. 仓库实际收到了多少；
5. 哪些条码已经绑定；
6. 换货补发的是哪个产品码；
7. 补发运单和旧货退回运单分别是什么；
8. 当前状态是由哪条仓库或发货事实推进的。

这条链路收清楚以后，销售退货、销售换货、仓库入库、发货补发、客户售后追踪才能连成一条可信的主链。

## 12. 本轮回溯后的职责契约

本轮修正后，四类数据的职责必须保持分离：

| 数据对象 | 权威职责 | 不应该承担的职责 |
| --- | --- | --- |
| `SalesOrder` / `SalesOrderLine` | 原始销售事实、交付数量、订单行身份 | 不直接保存退货或换货执行流水 |
| `POST /sales-orders/after-sales-summary` | 源订单页的行级售后读模型、数量统计、关联单号引用 | 不作为退货/换货写入入口 |
| `SalesReturn` / `SalesExchange` | 售后申请事实、行级产品快照、物流和业务状态 | 不直接修改库存数量 |
| `InboundRecord` / `ShipmentRecord` | 仓库入库、库存扣减、补发出库的不可变执行事实 | 不负责替代售后单据状态 |
| `inventory_command_service.go` | 库存数量、成本、流水、凭证和审计的事务写入口 | 不负责判断退货/换货业务是否允许执行 |

页面读取规则：

1. 源订单卡片的“已申请、已入库、旧货已收、补发已出、最新状态、关联单数”只读售后摘要。
2. 摘要返回的 `relatedReturns[]` / `relatedExchanges[]` 只提供业务引用 ID 和行级数量，不要求记录必须出现在当前分页列表。
3. 点击查看、确认入库、旧货入库或补发时，按引用 ID 懒加载完整售后单；详情加载不依赖当前列表页是否包含该记录。
4. 分页退货/换货列表只作为查询视图和快速缓存，不能再作为源订单卡片统计的事实来源。

## 13. 执行一致性契约

### 13.1 请求重放

退货入库、换货旧货入库、换货补发均要求前端传 `clientRequestId`。服务端将其规范化后写入执行记录的 `execution_key`，唯一范围为：

```text
source_type + source_id + source_line_id + execution_key
```

同一个请求在售后单行被重复提交时，服务端返回原执行记录，不再次：

- 增加库存；
- 扣减库存；
- 增加售后已收/已发数量；
- 写入重复条码；
- 生成重复审计事实。

每个执行记录同时保存规范化请求指纹。相同 `clientRequestId` 但请求行、数量、仓库、批次、物流或条码不同，会直接返回冲突，不会把旧结果伪装成新请求成功。

服务端自动补齐的当前时间不是客户端请求载荷的一部分。客户端省略入库/出库日期后，用同一个 `clientRequestId` 重试仍视为同一请求，不会因为两次重试发生在不同秒数而被错误拒绝。

服务端先锁定售后单头，再检查执行键，再执行库存事务。若发现历史上存在部分执行记录，直接拒绝重试并要求人工核查，不静默补写。

### 13.2 条码规范化和绑定

退货条码与换货标签码统一执行：

```text
Trim -> Uppercase
```

同一退货单或换货单内，规范化后的条码不能跨行复用。对换货而言，`OLD_ITEM` 与 `REPLACEMENT_ITEM` 也必须明确记录在同一标签事实中。未匹配标签在后续人工明确订单行后，原地转为 `Matched`，不能另插一条看似新的标签记录。

### 13.3 财务凭证边界

普通采购入库仍按库存服务原有规则生成入库凭证。售后退货和换货旧货入库因为没有采购成本，使用售后执行入口显式跳过零成本凭证；该选项不能放在普通 `RecordInbound` 的全局默认路径里。

换货补发必须进入共享库存出库事务，库存扣减、成本、出库流水、审计和售后补发数量在同一事务内完成。换货服务只负责：

1. 校验旧货是否已按行收齐；
2. 解析补发产品；
3. 调用库存出库事务；
4. 回写换货行和单头状态。

通用库存接口拒绝 `SALES_RETURN`、`SALES_EXCHANGE_OLD_ITEM`、`SALES_EXCHANGE_REPLACEMENT` 三类保留来源，不能通过通用入库、出库草稿、提交或作废接口绕过售后服务。换货补发出库的作废/冲销由换货专用服务完成：

```text
POST /sales-exchanges/:salesExchangeId/replacement-shipment/:shipmentId/void
```

该接口只允许冲销 `COMMITTED` 的换货补发流水，在同一事务中回滚库存、将原出库流水置为 `VOID`、扣回对应换货行的 `replacementShippedQuantity`，并重新计算换货状态；不会回退销售订单的 `deliveredQty`。冲销必须记录原因和审计事实。

## 14. 数据库迁移和历史数据边界

当前项目使用 `AutoMigrate` 加启动期 PostgreSQL 约束收口：

1. 新增售后条码表、执行来源字段、执行键字段和行级数量字段；
2. 使用 PostgreSQL advisory lock 串行化规范化和索引创建；
3. 启动时先将历史条码规范化为 `Trim + Uppercase`；
4. 发现同一售后单内已有规范化重复条码时，迁移失败并保留数据现场；
5. 执行键和售后单内条码唯一索引创建成功后，服务才继续启动。

需要特别区分两类历史数据：

- 有完整 `source_type/source_id/source_line_id` 的新执行记录，可以由系统继续追踪；
- 旧版本只写库存、没有售后来源行锚点的入库/出库记录，系统不能安全猜测它属于哪个退货或换货行，必须通过人工对账或一次性数据修复任务补齐。

因此，不能用“把旧列表重新计算一次”冒充历史数据迁移。正式上线前必须在真实 PostgreSQL 备份副本上验证：

1. `AutoMigrate` 新列和新表可重复执行；
2. 规范化后没有重复条码；
3. 唯一索引创建成功；
4. 旧数据中无法建立行级来源的记录已经列入对账清单；
5. 两个应用实例同时启动时不会并发破坏索引或规范化结果。
6. 新执行记录的请求指纹字段已完成迁移，旧记录指纹为空时只能按执行键兼容重放，不能据此推断旧请求载荷。
