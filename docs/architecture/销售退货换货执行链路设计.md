# 销售退货 / 销售换货执行链路设计

> 文档状态：业务规则与页面形态确认稿，待按此收口现有退货/换货页面与后端模型<br>
> 确认日期：2026-07-28<br>
> 适用范围：销售退货、销售换货、售后条码录入、仓库退回入库、换货补发、订单行级售后追踪

## 1. 结论先行

销售退货和销售换货不能只挂在销售订单头上。真正可操作的对象必须是销售订单明细行：

```text
SalesOrder
  SalesOrderLine 1  产品 A
  SalesOrderLine 2  产品 B
  SalesOrderLine 3  产品 C

退货 / 换货动作必须精确绑定到 SalesOrderLine
```

如果只记录 `salesOrderId`，一个订单里有多个产品、多行同产品或分批交付时，系统无法判断到底退的是哪一行、换的是哪一行、仓库收到的条码应该冲哪一行。后续库存、应收冲减、售后追踪都会错位。

核心决策如下：

1. 退货、换货必须以 `salesOrderLineId` 为行级锚点。
2. 产品码和条码要分清：
   - 产品码是 SKU / 型号 / 产品快照；
   - 条码 / 标签码是退回或补发实物的识别码。
3. 退货条码可以创建退货时先录入，也可以等仓库收到退货后再录入。
4. 换货既有旧货退回链路，也有新货补发链路，必须同时记录：
   - 旧货退回运单号；
   - 旧货条码 / 标签码；
   - 补发产品码；
   - 补发运单号；
   - 补发条码 / 标签码。
5. 仓库收到退货或旧货后，入库事实必须回写退货/换货状态，不能只改仓库库存。
6. “销售退货草稿 / 销售换货草稿”不应作为主页面的独立大列表。主视图应以源订单卡片为入口，在相关订单卡片或订单行里直接显示退货/换货状态列和关联单据。

## 2. 当前页面问题

当前退货/换货页面存在几个结构性问题：

| 问题 | 影响 |
| --- | --- |
| 源订单卡片只显示订单头信息 | 多行产品时无法直接知道哪一行可退、哪一行可换 |
| 右侧面板容易重复订单摘要 | 面板没有承担录入、追踪或行级操作职责 |
| 底部独立“已创建退货单 / 换货草稿”大区 | 用户必须离开源订单上下文才能看售后结果，信息被拆散 |
| 换货被按退货方式套用 | 忽略了补发产品码、补发运单号、旧货条码和新货条码 |
| 条码录入时机不清楚 | 不知道创建时录入、仓库收货时录入、还是两边都能录入 |

正确方向是：页面围绕“订单行售后状态”组织，而不是围绕“另一个草稿列表”组织。

## 3. 页面形态决策

### 3.1 退货页主视图

退货页展示源订单卡片，但卡片内部必须展开到行级：

```text
订单 ZP6AGS26050003
  客户 / 日期 / 状态 / 总数量

  行号  产品码  产品名称  已交付  已申请退货  已入库退货  可退数量  最新退货状态  操作
  1     A001    ...      20      5           3           15        部分入库      发起退货
  2     B002    ...      10      0           0           10        无            发起退货
```

只在退货页显示退货相关列，不污染销售订单主页面。

点击订单行或“发起退货”后进入退货操作面板，面板职责是：

1. 选择本次退货数量；
2. 可选录入退回物流单号；
3. 可选录入退回条码 / 标签码；
4. 录入退货原因、异常分类、凭证；
5. 创建真实退货单。

已经创建的退货单不放到下面独立占位区作为主入口，而是在源订单卡片的对应行下显示关联记录：

```text
行 1 关联退货：
  TH20260728001  申请 5 / 已入库 3  待补物流  查看 / 补录 / 收起
```

### 3.2 换货页主视图

换货页也以源订单卡片为入口，但显示换货相关列：

```text
订单 ZP6AGS26050003
  行号  原产品码  产品名称  已交付  已换货  可换数量  补发产品码  旧货运单  补发运单  换货状态  操作
  1     A001      ...      20      2       18        A001-R       SF...     YT...     补发中    发起换货
```

点击订单行或“发起换货”后进入换货操作面板，面板职责是：

1. 选择具体订单行；
2. 填写换货数量；
3. 录入旧货退回运单号；
4. 录入旧货条码 / 标签码；
5. 录入补发产品码；
6. 录入补发运单号；
7. 录入补发条码 / 标签码；
8. 录入换货原因、备注、凭证。

换货和退货不同：退货只处理“客户退回什么”；换货同时处理“客户退回什么”和“我们补发什么”。

### 3.3 关于草稿列表

“草稿”可以存在于弹窗或表单的本地未提交状态，但不应作为页面主视图的大列表。

建议收口为：

| 对象 | 是否需要独立主列表 | 原因 |
| --- | --- | --- |
| 销售退货单 | 不作为当前页面主入口；可作为高级查询页或筛选结果 | 退货单应直接挂回订单行上下文 |
| 销售换货单 | 不作为当前页面主入口；可作为高级查询页或筛选结果 | 换货单必须回到源订单行和补发明细 |
| 草稿 | 不建议落成主列表 | 草稿容易变成第二套业务事实，和源订单状态脱节 |

如果后续确实需要“全部退货单 / 全部换货单”查询，可以做成独立查询视图，而不是压在源订单操作页底部。

## 4. 数据模型边界

### 4.1 退货模型

```text
SalesReturn
  id
  returnNo
  salesOrderId
  customerId / customerName
  status
  returnDate
  trackingNo
  carrier
  shippedAt
  logisticsNote
  reason / remarks
  totalRequestedQuantity
  totalReceivedQuantity

SalesReturnLine
  id
  salesReturnId
  salesOrderLineId
  lineNo
  productId
  productCodeSnapshot
  productNameSnapshot
  requestedQuantity
  receivedQuantity
  returnableQuantitySnapshot
  status

SalesReturnLineBarcode
  id
  salesReturnLineId
  rawCode
  normalizedCode
  productCodeSnapshot
  bindSource: CREATE_FORM | WAREHOUSE_SCAN | MANUAL_REVIEW
  verificationStatus: PENDING | MATCHED | MISMATCHED | MANUAL_CONFIRMED
  boundAt
  boundBy
```

退货创建时可以只创建 `SalesReturn` 和 `SalesReturnLine`，条码可以为空。仓库收到货后再扫描条码并补写 `SalesReturnLineBarcode`。

### 4.2 换货模型

```text
SalesExchange
  id
  exchangeNo
  sourceSalesOrderId
  customerId / customerName
  status
  exchangeDate
  expectedReplacementDate
  receivedOldItemTrackingNo
  replacementTrackingNo
  exchangeReason
  exchangeRemarks

SalesExchangeLine
  id
  salesExchangeId
  salesOrderLineId
  lineNo
  originalProductCodeSnapshot
  replacementProductCode
  replacementProductModel
  exchangeQuantity
  oldItemReceivedQuantity
  replacementShippedQuantity
  status

SalesExchangeLineBarcode
  id
  salesExchangeLineId
  side: OLD_ITEM | REPLACEMENT_ITEM
  rawCode
  normalizedCode
  productCodeSnapshot
  bindSource: CREATE_FORM | WAREHOUSE_SCAN | SHIPMENT_SCAN | MANUAL_REVIEW
  verificationStatus: PENDING | MATCHED | MISMATCHED | MANUAL_CONFIRMED
  boundAt
  boundBy
```

换货行必须同时知道：

1. 原订单行是哪一行；
2. 原产品码是什么；
3. 补发产品码是什么；
4. 旧货收到多少；
5. 新货补发多少；
6. 哪些条码属于旧货，哪些条码属于补发货。

## 5. 条码和产品码绑定规则

### 5.1 退货条码录入时机

退货条码支持两种时机：

| 时机 | 场景 | 系统动作 |
| --- | --- | --- |
| 创建退货时先录入 | 客户已经提供条码、照片或面单 | 先写入 `SalesReturnLineBarcode`，状态为 `PENDING` |
| 仓库收到后录入 | 客户没有提前提供，仓库实物到达后扫码 | 仓库入库时创建或补写 `SalesReturnLineBarcode` |

两种方式最终都必须绑定到 `salesReturnLineId`，不能只挂到退货单头。

### 5.2 仓库扫码如何绑定到订单行

仓库收到退货或换货旧货时，扫码解析优先级：

1. 如果条码能反查到原发货记录或销售订单行，直接绑定对应 `salesOrderLineId`。
2. 如果条码包含产品码，只能定位到产品，系统在当前退货/换货单内筛选相同产品码的行。
3. 如果只有一条候选行，自动绑定。
4. 如果有多条候选行，必须让仓库人员选择行号，不能静默绑定。
5. 如果没有候选行，进入 `MANUAL_REVIEW`，不得更新已入库数量。

任何模糊绑定都必须显式处理，不能为了省一步把条码挂到订单头。

### 5.3 产品码和条码不能混用

产品码用于确认“是什么产品”；条码用于确认“是哪一件 / 哪一箱 / 哪个标签”。

退货：

```text
SalesReturnLine.productCodeSnapshot = 要退的产品
SalesReturnLineBarcode.normalizedCode = 退回实物条码
```

换货：

```text
SalesExchangeLine.originalProductCodeSnapshot = 客户退回的原产品
SalesExchangeLine.replacementProductCode = 我们补发的产品
SalesExchangeLineBarcode(side=OLD_ITEM) = 旧货条码
SalesExchangeLineBarcode(side=REPLACEMENT_ITEM) = 补发货条码
```

## 6. 状态流转

### 6.1 退货状态

退货状态建议拆成单头状态和行状态。

单头状态：

```text
Created
AwaitingReturn
InTransit
PartiallyReceived
Received
Closed
Canceled
```

行状态：

```text
Requested
PartiallyReceived
Received
MismatchPendingReview
Canceled
```

状态推进规则：

1. 创建退货单后进入 `Created` 或 `AwaitingReturn`。
2. 录入退回运单号后可进入 `InTransit`。
3. 仓库入库一部分后进入 `PartiallyReceived`。
4. 所有退货行 `receivedQuantity >= requestedQuantity` 后进入 `Received`。
5. 财务冲减、退款或售后关闭后进入 `Closed`。

### 6.2 换货状态

换货状态不能复用退货状态，建议：

```text
Created
AwaitingOldItem
OldItemInTransit
OldItemPartiallyReceived
OldItemReceived
ReplacementPreparing
ReplacementShipped
Closed
Canceled
```

换货至少有两条物流线：

| 物流线 | 字段 | 状态影响 |
| --- | --- | --- |
| 客户退回旧货 | `receivedOldItemTrackingNo` | 推进旧货在途、旧货已收 |
| 我方补发新货 | `replacementTrackingNo` | 推进补发准备、补发已发 |

旧货入库不等于换货完成。只有旧货处理和补发处理都完成后，换货才能关闭。

## 7. 仓库入库与状态同步

仓库收到退货或换货旧货时，不能只写库存入库。必须生成售后入库事实并回写售后单据。

建议链路：

```text
仓库扫码收货
  解析条码 / 产品码
  定位 SalesReturnLine 或 SalesExchangeLine
  校验数量和产品是否匹配
  写入 WarehouseInboundRecord
  写入 Return/Exchange Line Barcode Binding
  更新 line.receivedQuantity
  更新单头状态
  发出 AfterSalesInboundConfirmed 事件
```

库存入库是仓库事实；退货/换货状态是售后事实。二者通过同一个事务或同一个可靠事件保持一致。

### 7.1 退货入库回写

```text
WarehouseInboundRecord
  sourceType: SALES_RETURN
  sourceId: salesReturnId
  sourceLineId: salesReturnLineId

提交后：
  SalesReturnLine.receivedQuantity += inboundQuantity
  SalesReturn.status 重新计算
  SalesOrderLine.returnedQuantity / receivedReturnQuantity 同步更新
```

### 7.2 换货旧货入库回写

```text
WarehouseInboundRecord
  sourceType: SALES_EXCHANGE_OLD_ITEM
  sourceId: salesExchangeId
  sourceLineId: salesExchangeLineId

提交后：
  SalesExchangeLine.oldItemReceivedQuantity += inboundQuantity
  SalesExchange.status 重新计算
```

### 7.3 换货补发出库回写

补发新货不应该通过退货入库逻辑处理。它应该走出库 / 发货链路：

```text
ShipmentRecord
  sourceType: SALES_EXCHANGE_REPLACEMENT
  sourceId: salesExchangeId
  sourceLineId: salesExchangeLineId
  productCode: replacementProductCode

提交后：
  SalesExchangeLine.replacementShippedQuantity += shippedQuantity
  SalesExchange.replacementTrackingNo 更新
  SalesExchange.status 重新计算
```

## 8. API 建议

### 8.1 源订单售后摘要

```text
GET /sales-orders/:id/after-sales-summary
```

返回每个订单行的退货/换货摘要：

```text
salesOrderLineId
lineNo
productCode
deliveredQuantity
returnRequestedQuantity
returnReceivedQuantity
exchangeRequestedQuantity
oldItemReceivedQuantity
replacementShippedQuantity
latestReturnStatus
latestExchangeStatus
relatedReturns[]
relatedExchanges[]
```

页面用这个接口在订单卡片行内显示售后列，不需要底部再做一个孤立草稿列表。

### 8.2 退货

```text
POST   /sales-orders/:salesOrderId/returns
GET    /sales-returns/:id
PATCH  /sales-returns/:id/logistics
POST   /sales-returns/:id/line-barcodes
POST   /warehouse/inbounds/sales-return
```

创建退货时 `lines[]` 必须包含：

```text
salesOrderLineId
quantity
optional barcodes[]
```

### 8.3 换货

```text
POST   /sales-orders/:salesOrderId/exchanges
GET    /sales-exchanges/:id
PATCH  /sales-exchanges/:id/old-item-logistics
PATCH  /sales-exchanges/:id/replacement-shipment
POST   /sales-exchanges/:id/line-barcodes
POST   /warehouse/inbounds/sales-exchange-old-item
POST   /shipments/sales-exchange-replacement
```

创建换货时 `lines[]` 必须包含：

```text
salesOrderLineId
exchangeQuantity
replacementProductCode
optional oldItemBarcodes[]
optional replacementBarcodes[]
```

## 9. 前端落地顺序

### P0：先纠正页面信息架构

1. 退货页去掉底部“已创建真实销售退货单”的主占位布局。
2. 换货页去掉底部“销售换货草稿”的主占位布局。
3. 源订单卡片展开订单行。
4. 退货页只显示退货相关列。
5. 换货页只显示换货相关列。
6. 点击具体订单行后打开行级操作面板，不再只选订单头。

### P1：补行级创建能力

1. 退货创建必须按 `salesOrderLineId` 填数量。
2. 换货创建必须按 `salesOrderLineId` 填数量和补发产品码。
3. 条码录入必须挂到具体行。
4. 多行同产品时必须让用户明确选择行号。

### P2：补仓库同步

1. 退货入库后回写退货行状态。
2. 换货旧货入库后回写换货行状态。
3. 换货补发出库后回写换货行状态。
4. 状态更新必须来自仓库/发货事实，不允许前端只手动改状态。

### P3：补查询和追踪

1. 订单行内展开关联退货/换货记录。
2. 售后单详情展示条码绑定历史、入库流水、补发流水。
3. 订单分析和客户摘要读取行级售后汇总。

## 10. 不能做的短期捷径

| 捷径 | 为什么不能做 |
| --- | --- |
| 只保存 `salesOrderId` 不保存 `salesOrderLineId` | 多产品订单会无法准确退换 |
| 把条码挂到订单头 | 仓库入库后无法知道冲哪一行 |
| 用草稿列表当主视图 | 售后事实会脱离源订单上下文 |
| 退货和换货共用同一套表单 | 换货需要补发产品码、补发运单和新货条码 |
| 仓库入库只改库存不回写售后单 | 页面状态永远不同步 |
| 产品码匹配不唯一时自动绑定 | 会造成错误入库和错误售后数量 |

## 11. 最终目标

退货和换货页面最终应该让用户一眼看到：

1. 哪张订单的哪一行还能退；
2. 哪张订单的哪一行还能换；
3. 已经申请了多少；
4. 仓库实际收到了多少；
5. 哪些条码已经绑定；
6. 换货补发的是哪个产品码；
7. 补发运单和旧货退回运单分别是什么；
8. 当前状态是由哪条仓库或发货事实推进的。

这条链路收清楚以后，销售退货、销售换货、仓库入库、发货补发、客户售后追踪才能连成一条可信的主链。
