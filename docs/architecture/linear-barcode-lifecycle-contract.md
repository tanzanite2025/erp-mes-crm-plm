# 产品编码（Code128 / QR Code）生命周期契约

2026-11-09 检验站与扫码位置确认：品质标准中的“环节”统一指品质所属的检验站，系统默认写入成型检验站、机加检验站、精细检验站、涂装检验站，并允许配置。四站也是实际扫码的地点，扫码发生在相应站点转往下一环节的阶段。内部结构为“检验站 → 重量项目 → 等级规则”；品检站 ID、生产路线节点 ID、工序 ID 分别表达，扫码业务可引用品检站身份。当前已实现目录及规则配置，四站扫码录入与流转不能视为已经接通。

## 适用范围

本契约说明以下编码及生命周期入口之间的数据所有权和关联方式：

- 基础设置的协议规则 TAB
- 编码中心的产品编码打印 TAB
- 编码中心的编码状态 TAB
- 编码中心的产品编码操作手册
- 裁剪作业的产品绑定 TAB
- 生产执行的扫码命令和产品编码生产履历查询

它是编码库存与产品编码生产履历之间数据边界的权威说明。各 feature 的 README 只描述本地职责，不复制本文件的状态机。前端状态定义页不得维护完整状态数组；页面必须读取后端只读契约 `GET /code-center/linear-barcode/status-contract`。侧边栏业务名称为“产品编码”，内部路由仍使用 `linear-barcode`。

## 码相关文件的依赖边界

公共编码能力统一放在 `src/lib/product-code/`：`product-code-protocol.ts` 定义 15 位字段和拼接规则，`product-code-parser.ts` 提供字段与显示解析，`issued-product-code-inventory-contracts.ts` 定义已签发记录和库存契约，`product-code-label-readable-text-formatter.ts` 只负责标签可读文字。这些文件不依赖基础设置、打印或工序 feature。

基础设置保留协议配置、规则默认值和模拟输入；真实签发与库存查询继续由现有打印批次 API 适配。公共记录类型从该 API 服务独立，后续扫码、工序和追溯模块无须为了引用编码字段或记录类型依赖打印服务。`parseProductCodeForDisplay` 的 `isValid` 保持原有长度检查语义，预览流水占位符也可显示；它不验证编码是否已签发、是否允许绑定或是否可以流转。

编码中心的 `product-code-label-print-executor.ts` 负责签发后的标签准备与失败补偿，`product-code-label-print-preview.ts` 负责打印窗口与版式，`product-code-label-print-quantity-constraints.ts` 负责打印数量约束。已有编码补打保持独立只读服务。统一双码绘制器只接收原始编码，不读取业务状态；标签文字格式化器不重新生成产品编码。

生产执行已通过已保存的原始 `code` 关联自己的业务记录；后续生命周期模块也应使用同一产品编码关联各自事实。库存记录 `id` 的含义仍是库存行 ID。这里不新增产品实体表或通用生命周期引擎，也不把打印库存状态扩大为工序执行状态。具体文件所有权见[编码中心 README](../../src/features/code-center/README.md)。

## 15 位协议

固定结构：

```text
年2 + 月1 + 日2 + 型号2 + 外观1 + 孔型1 + 孔数2 + 流水4
```

真实流水号只能由后端从持久化协议配置读取发号规则后生成。客户端不能提交发号规则键，也不能自行保留或递增流水号。

## 同一产品编码的一维码与二维码展示及状态继承

Code128 与 QR Code 是同一枚 15 位产品编码的两种图形表达。新签发批次只执行一次既有发号事务，每个 `item.code` 同时交给两种绘制器；二维码内容是该原始编码字符串。N 枚产品编码对应 N 条库存记录和 N 对码图，图形类型不建立独立流水号、库存或状态机。

因此二维码不建立自己的状态。打印库存状态仍由 `linear_barcode_inventory_items.code` 对应的那一条库存记录提供，生产执行状态仍由 `product_barcode_states.product_barcode` 对应的那一条状态记录提供。扫描二维码后得到同一个原始字符串，进入与扫描 Code128 完全相同的查询、绑定、工序执行和状态事件链路。状态 TAB 展示的是这套产品编码状态契约，Code128 和 QR 只是两个扫描入口。

同一打印页面的单行、整单和失败重试入口共用同步执行保护，执行期间锁定订单和数量，防止交叉点击重复签发或将完成结果写入其他订单。执行成功或失败后均释放保护；已成功生成预览的行不再次签发，已有编码通过库存补打。

规则模拟、库存预览和打印复用统一双码绘制服务。打印窗口可选择一维码、二维码或同标签双码排版，切换排版不调用发号接口。单码使用 70 × 30 mm 标签，双码使用 90 × 35 mm 标签；二维码保持正方形及四模块静区，Code128 左右各保留十个窄条模块静区。渲染库的留白单位为点，需按码制模块尺寸换算，并以实际输出验证。

已有库存补打使用独立只读路径，只绘制原有编码；允许未过期的 `AVAILABLE` 和 `BOUND`，拒绝 `EXPIRED`、`SCRAPPED` 以及已到期的待绑定码。补打不创建批次、不修改有效期或状态，渲染失败也不报废已有批次。新签发流程的渲染失败继续沿用既有批次报废逻辑。

## 库存状态机

一维码预打与 MRP、裁纱共用有效销售订单条件：`Pending`、`Scheduling`、`InProgress`；排除草稿、已完成、已作废、软删除和报价。订单确认后即可预打，不要求手工进入排产。预打仅创建条码库存，不推进销售订单生产状态。

```text
打印签发
  -> AVAILABLE
       -> BOUND      产品绑定事务成功
       -> EXPIRED    该产品码被扫描绑定时发现 expiresAt 已到期
       -> SCRAPPED   所属打印批次被报废
```

约束：

- `BOUND`、`EXPIRED`、`SCRAPPED` 都是终态，不能恢复为 `AVAILABLE`。
- 产品绑定只接受已逐码落库且状态为 `AVAILABLE` 的产品码。
- `BOUND` 更新、绑定记录、绑定事件和打印批次激活计数必须处于同一事务。
- 报废批次只把仍为 `AVAILABLE` 的码转为 `SCRAPPED`，不能覆盖已绑定或已过期记录。

## 生产执行状态机

生产执行状态不是打印库存状态的扩展，也不是产品绑定或裁纱/卷材追溯的硬前置。它描述产品编码在生产链路中的执行状态：

```text
NOT_STARTED
  -> IN_PROGRESS
       -> COMPLETED
       -> HOLD
       -> REWORK
```

约束：

- 生产执行状态的产品编码事实源是 `product_barcode_states` 和 `product_barcode_state_events`。
- `status` 是一级状态，当前环节必须通过二级定位表达：`routeStepId` 表示路线中的具体工序位置，`currentProcessStepId` 表示该位置对应的工序库身份。
- 当前路线位置通过 `routeStepId` 定位，步骤对应的工序身份通过 `processStepId` 表达；同一工序可在不同路线位置出现，不能用工序 ID 替代路线位置。
- 生产计划继承来源订单行选择的产品分类展示上下文、有效 MBOM 分支及默认/自定义路线，并保存排产时固定的路线快照；产品码通过活跃执行批次关联计划。产品分类只用于人员理解、检索和展示，`Product.typeId` 用于校验 MBOM 分支所属分类，不单独决定工序或路线；实际生产约束落在具体 MBOM 稳定分支。MBOM 分支工序及顺序构成默认路线；只有订单对应 EMBOM 需要个性调整时，订单行才选择本单自定义路线，路线配置直接关联订单行。扫码按条码读取计划固定路线，首次开工由服务端选择首步；客户端不提交批次、路线或当前工序身份。订单行分支选择和路线方式、订单行自定义路线、计划继承，以及 MRP／正式领料按已选分支限定配方均已实现；端到端验收另行跟进，详见[生产线主数据与订单路线分阶段实施设计](生产线主数据与订单路线分阶段实施设计.md)。
- 状态变化应通过扫码、工序执行、转移或带审计的纠错命令写入；编码状态 TAB 只读展示契约，不直接改某个编码状态。

生产执行页通过 `GET /production/product-barcode-lifecycle/:productBarcode` 只读查询当前状态，并并列读取该产品码的状态事件、工序操作和生产流转事件。三类记录分别计数和分页；页面按关联操作归并展示，当前状态对应事件优先标记。该接口不读取产品绑定事件；绑定记录由独立的 `GET /production/product-barcode-bindings?productBarcode=...` 查询。两边以规范化产品编码关联，当前没有统一的跨域时间线。读取生产履历不会写入事实，也不代表品检、仓储或售后履历已经接入。

### 当前已核对的数据链（2026-11-14）

```text
同一产品编码
  ├─ 库存链：签发 -> AVAILABLE ->（可选）产品绑定 -> BOUND
  └─ 生产链：扫码/初始化 -> product_barcode_states
                         -> production_operation_executions
                         -> product_barcode_state_events
```

- Code128 与 QR Code 解码为同一个原始产品编码；规范化后使用同一个 `productBarcode` 作为库存、绑定和生产事实的关联值。
- 产品绑定事务只建立产品码与已激活预浸料卷实例之间的关系，不记录裁纱执行单 ID。产品绑定不是普通生产开工的强制前置。
- 首次 `START` 将产品码规范化为大写并去除首尾空白；操作、状态和状态事件使用相同规范化编码，并在一个生产事务中提交。生产命令回执与其副作用在同一事务内提交。
- 相同幂等键和相同规范化请求重放时返回已保存的响应，不重复创建生产操作或事件；相同键用于不同请求时返回冲突。
- 当前状态为 `IN_PROGRESS` 时，新幂等键发起的再次 `START` 属于无效状态转换，服务端拒绝且不新增操作、状态事件或命令回执；相同幂等键的原请求重放仍返回原响应。`HOLD` 或 `REWORK` 后可通过 `START` 恢复或开始返工；同一已完成工序必须先显式执行 `REWORK`，不能直接再次开工。
- 同一码、同执行轮次、同路线节点的 `COMPLETE` 即使使用新扫码请求键再次提交，也复用已有完工操作。其扫码副作用已应用时，只读回该操作已有的流转事实并恢复推进结果，不重复新增状态事件、路线流转、审计或再次推进当前位置；末道工序重试仍返回路线已完成。
- 生产开工只写生产域事实，不改变 `linear_barcode_inventory_items` 的 `BOUND` 状态、库存版本、`print_batches.activated_count` 或批次版本。
- 当前已核验首次 `START`、相同请求重放、不同请求键重复开工冲突、不同请求键重复完工、手工完工后扫码补办路线效果、暂停后恢复、完成后返工轮次、路线推进事务、生产状态查询和绑定库存原子性；尚未把绑定事件与生产事件合并为统一跨域履历，品检、仓储及售后履历也不属于当前生产查询。

本段验证覆盖：服务端生产服务全量测试（包含首次扫码、相同请求重放、不同请求键重复开工冲突和重复完工、手工完工后的扫码效果补办、路线推进回滚、返工轮次及暂停后恢复）；前端生产执行确认工作流与产品码生产履历查询测试。它确认上述数据链边界，不代表所有工序或完整产品生命周期已验收。

## 品质规则引用与生产扫码录入边界（2026-11-09）

品质标准的重量规则编辑已按“检验站 → 重量标准项目 → 等级规则”分组并完成保存回读验证，范围属于具体产品的品质标准版本。品质目录的 `inspectionStageId` 标识品质检验站，也可由本站扫码业务引用；它与生产路线的 `routeStepId`、工序的 `processStepId` 分别表达，不能混用。

现场扫码的地点是成型、机加、精细、涂装四个品检站，扫码发生在相应站点转往下一环节的阶段。现场工作中先人工书写的记录，在扫码录入时按实际要求填写；产品跟踪单中的生产工序信息仍由相应来源业务持有，品质提供独立的重量标准与服务端判定。卷制、组合、成型完成后可集中填写多个已完成工序的记录，但不能据此推断四站共用一个外部转录地点。每个扫码点具体录入哪些内容应逐项对齐，不能只凭条码当前路线节点决定全部待填内容。实际执行或过站仍复用既有条码状态事实源及统一执行命令，不放宽路线校验；扫码识别本身不直接等于工序完成。

记录需保留引用的标准版本、项目、实测和判定依据。当前四个品检站的扫码录入与品质规则引用尚未接通；原有通用检验入口和统一扫码命令不能作为已具备产品跟踪单录入的证明。后续自动读秤只作为录入端取值方式，不进入品质标准维护。

不合格报警、品质处置和是否允许进入下一环节分开表达。本次文档对齐不改变现有条码状态机；实际流转由既有执行命令核验相应依据，标准配置界面不直接推进或改写条码状态。逐项状态与验收统一见[品质检验站配置文档](../frontend/quality-standard-configurable-inspection-stage-catalog-and-item-name-snapshots.md)的“逐项对齐顺序与验收”。

## 过期判定边界

系统不得创建一维码库存定时扫描任务，也不得在打印新批次或查询库存列表时顺便扫描整张库存表。

过期采用业务事件驱动：

1. 操作员扫描预浸料二维码和产品一维码并提交绑定。
2. 后端只针对当前扫描的产品码检查 `status` 和 `expiresAt`。
3. 若当前码仍为 `AVAILABLE` 且已到期，只把这一枚码更新为 `EXPIRED`，随后拒绝绑定。
4. 未被扫描的其它库存码不发生状态写入或额外计算。

这样允许一次预打几百张并按生产节奏慢慢使用，同时避免无业务事件时反复更新库存。

## 事务与幂等

- 批量签发必须在一个事务内完成连续发号、打印批次创建和逐码库存创建。
- 产品绑定必须锁定当前产品码库存行，防止同一码并发绑定到不同预浸料卷。
- 相同产品码和相同预浸料卷的重复提交返回原绑定记录，不能重复增加批次激活计数。
- 未签发码返回未找到；过期码拒绝绑定；已绑定或已报废码返回冲突。

## 修改检查清单

修改下列任一内容时，必须同时核对本契约和回归测试：

- 15 位字段结构或解析器
- Code128 与 QR 是否继续解码为同一原始产品编码

- `AVAILABLE / BOUND / EXPIRED / SCRAPPED` 转换
- 产品绑定事务或打印批次激活计数
- 首次 `START` 的产品编码规范化、事务原子性、幂等重放及库存不变性
