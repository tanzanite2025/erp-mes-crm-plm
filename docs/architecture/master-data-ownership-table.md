# Master Data Ownership Table (Field -> Module -> Read Entry)

Updated: 2026-10-27 (production material warehouse and dedicated pending-consumption custody destination)
Scope: `src/**`, module services in `server/services/**`, and current master-data initialization in `server/db/db.go` and `server/db/unit_seed.go`.

## 1) Rules

1. Fixed business enums: no TAB, no public dictionary; keep in module-owned readonly code.
2. Maintainable master data: must belong to one business module; module owns both write and read entry.
3. Global exceptions are rare (example: units).
4. Public dictionary is compatibility-only, not business source of truth.

Each product template owns its attribute definitions and options. Templates may use equal category keys and option values without sharing records. Products store individual selections; labels are resolved within the owning template. Product Templates edits the entire template draft transactionally. BOM performance version choices remain an independent catalog and are maintained beside the performance version field in the BOM form. There is no standalone product attribute route, public catalog entry, module TAB or compatibility redirect.

Product templates bind attribute categories and required settings; product forms select their option values. `techSeries`, `tireType` and `brakeType` are product specifications. The `product-structure` domain owns the performance-version business UI, service wrapper and query key. It reuses `engineering`'s option persistence contract under the fixed `versionLevel` category, filtering out template-owned options. This is a separate business catalog, not a new physical table. The server ensures the internal compatibility category exists when writing; users do not create or select product attribute categories. Each selected performance version is stored on its BOM. Product saves exclude this performance version from product attributes. See [product template attribute ownership and reuse](../frontend/product-template-attribute-classification-business-components-reuse-guide.md).

Weight is not a global property of a performance-version option or a base model (`typeId`). Each BOM stores its own weight and unit for its concrete product (`productId`). Comparison is scoped to the same product, BOM type and ownership (internal or the same customer), then grouped by performance version. Other versions may show saved BOM weights or unsaved session drafts; saving the current BOM does not persist those other versions. Shared sections classify materials; production routes own production steps, and the BOM structure protocol owns parent/child composition. See [BOM editor responsibilities](../frontend/bom-editor-dialog-product-information-recipe-layout-and-responsibility-boundaries.md).

Technical specification documents have one master library at `/engineering-db/specs`. The product's “绑定工艺” menu reads that library, previews its current document, and can open its shared selection and creation dialogs. Creating a document saves to the master library immediately; confirming selection changes the product draft, and saving the product persists `engineeringSpecId`. Cancelling selection does not delete a document already created in the master library. These are separate operations. Attachments use the server asset upload service, so browser-local `file-*` or temporary blob URLs cannot be persisted as master-library attachments. Old browser-local attachments must be uploaded again; no second document store or compatibility address is introduced. Document revision (`revisionNo`) is distinct from the concurrency counter (`version`). Master writes retain the existing engineering-spec audit trail and reject stale versions; referenced documents cannot be deleted.

Knowledge entries explain document purpose and link to the owning library; file preview, download, revision and authority remain with that library. Guide explanations and knowledge answers follow the [knowledge, guide and business document source ownership contract](knowledge-base-operation-guides-and-business-document-source-ownership-boundaries.md), which distinguishes current capabilities from planned content integration.

Production warehouse integration resolves fixed codes rather than names, list order or environment-specific IDs. Production issuance freezes the existing MRP required quantities and stores confirmed order-line allocations; the warehouse retains the single inventory balance and ledger. The pending-consumption destination receives matching outbound/inbound custody entries, not sales shipment or consumption facts. Initialization explicitly persists its disabled capabilities, preserves administrator suspension of inbound/outbound directions, and does not change other warehouse categories. General inventory writes cannot bypass its dedicated transfer transaction. See [confirmed warehouse movement, allocation and inventory custody contract](production-material-issuance-confirmed-warehouse-movements-order-line-allocation-and-custody-inventory-transfer-contract.md).

Technical specification list and detail query policies are owned by `engineering-db/queries/technical-specification-document-master-library-query-options.ts`. Its domain service owns document validation and field mapping; the generic engineering HTTP contract validates only common fields and object buckets. The server validates document field types before both create and PATCH, and full document saves persist empty descriptions and `false` values. Master-record descriptions remain authoritative even when empty; stale nested copies cannot restore cleared text. See [the architecture review, section 12](../frontend/product-creation-guide-architecture-and-file-responsibility-review.md#12-第三步绑定工艺复用工程管理技术规范主库).

Mold groups are an independent Equipment & Tooling master directory. Groups may exist before molds; molds and products reference their IDs. Group Management owns names, descriptions, availability and reference-protected deletion. Renaming preserves IDs and synchronizes display mirrors; deactivation retains existing links and prevents new assignments. Group creation, mold creation, confirming selection and saving a product are separate operations. Cancelling a draft retains already-created master records. Product and mold editors share the directory query and refresh group, mold and product caches after master writes. See [stable mold-group identity and legacy migration](mold-group-master-directory-stable-identity-product-bindings-and-legacy-migration.md).

All mold array consumers (Mold Management, drawing links, loans and product group selection) read the complete master library through `/molds?options=true`; their local filtering must not consume a default page as a complete directory. The shared group selector owns directory loading, retry and ID selection. Product persistence explicitly writes cleared group IDs and display mirrors in its original transaction, and product patch audits record actual field values. The compatibility `/molds/group-names` endpoint reads active master entries, including empty groups; names no longer create groups implicitly.

## 4) Forbidden Patterns (Effective Now)

1. No new `DictionaryCoreService` usage in business modules (`trading/material-archive/engineering/engineering-db/...`).
2. No new `xdfc_dictionary_updated` listeners in business modules.
3. No new full-snapshot reads (`DictionaryCoreService.getEntries()`) in business modules.
4. Cross-module read must go through explicit readonly module APIs/functions.

## 5) TAB Decision

1. Fixed enums: do not create TAB.
2. Maintainable master data: create module-internal TAB (not public dictionary TAB).
3. Only global exceptions keep global management entry.
