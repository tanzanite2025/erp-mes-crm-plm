# 生产路线步骤与计件工价实施准备与文件拆分计划

> 文档状态：实施基准与进度记录  
> 确认日期：2026-08-13  
> 业务模型基准：[`生产拓扑路线步骤与计件工价统一设计.md`](生产拓扑路线步骤与计件工价统一设计.md)  
> 目标：先稳定路线步骤和文件职责，再实现作业级计件；不把新逻辑继续堆入现有聚合文件  
> 当前进度：PR0、PR1、PR2 已完成；PR3 已完成契约与基础迁移实现；PR4 已完成计件记录快照服务并接入生产/扫码完工入口；剩余工作是 PR3 的真实 PostgreSQL 迁移验收。

## 1. 开始结论

当前不应继续给 `PieceworkRate` 或现有巨型服务打补丁。第一批实现只回答两个问题：

1. `ProductionRouteStep` 能否跨服务重启和路线修订保持稳定；
2. 后续拓扑、作业库、路线、工价和计件记录分别应该写进哪个明确边界。

计件粒度已经确定：

```text
LineSegment 工段
└─ 动态绑定一个或多个 ProcessStep 作业项目
   └─ ProductionRouteStep 选中具体作业
      └─ PieceworkRate 按作业或路线步骤计价
```

`LineSegment` 从来不是工价匹配键。成型工段只有一个“成型作业”时，界面可以扁平展示，但底层仍按该作业 ID 报工和计件。

## 2. 已核实的阻断项

### 2.1 启动迁移曾经会删除路线步骤表，现已解除

`server/db/db.go` 的 `InitDB()` 每次启动迁移前都会调用 `prepareProductionTopologySchema()`，该函数执行：

```sql
DROP TABLE IF EXISTS production_route_steps CASCADE
```

该问题已经在 PR0 处理：常规 `InitDB()` 启动路径不再调用这段破坏性准备逻辑，且增加了源码守卫测试。后续仍需在真实数据库环境核对历史孤儿 `routeStepId`，但不能再把“启动会删除路线步骤表”作为当前实现描述。

### 2.2 已发布路线的原地修改和删除已被阻止

PR2 已在 `server/services/production_route_service.go` 和 `server/services/production_route_lifecycle.go` 落地以下规则：

- `DRAFT` 路线可以编辑、增删路线步骤并发布；
- `PUBLISHED` 路线不能原地编辑，只允许完全一致地转为 `ARCHIVED`；
- `ARCHIVED` 路线只读；
- 已发布路线不能删除；
- 已被条码、执行、委外转移或委外检验事实引用的草稿路线不能删除；
- 草稿路线删除和路线步骤移除仍采用软删除，历史记录保留在数据库中。

当前仍未完成的是“发布后创建新路线修订”的产品流程。现有 `ProductionRoute.version` 仍同时承担行版本用途，不能在文档中误写成已经完成的路线家族/业务修订号模型。

### 2.3 生产主数据删除保护仍未完成

`DeleteProcessStep`、`DeleteProductionLine` 当前仍主要直接进入仓储删除。作业项目、工段或产线的引用保护应作为独立后续 PR，不要因为路线 PR2 已完成就误认为整个生产主数据删除保护已经完成。路线删除本身的状态和下游事实保护已由 PR2 覆盖。

### 2.4 计件前后端契约已完成第一轮收敛

后端 `PieceworkRate` 的 canonical 字段现在包括：

```text
productId
processStepId
routeStepId
unitPrice
currency
effectiveFrom
effectiveTo
status
remarks
version
```

`processCode`、`processName`、`piecePrice`、`effectiveAt` 仅作为读取兼容投影或边界适配字段保留，不再进入 PATCH canonical command。前端页面模型通过显式 API adapter 转换，写入只发送稳定 ID、`unitPrice` 和生效区间。

```text
productId
processStepId
routeStepId
unitPrice
unit
status
remarks
version
```

工价接口现已对齐为：

```text
GET    /piecework/rates
POST   /piecework/rates
PATCH  /piecework/rates/:id
DELETE /piecework/rates/:id
```

PATCH 使用 SDRTS `o/n` 差分和 `metadata.version`，删除也必须提供版本号。启动迁移会回填可确定的作业身份和生效起点，并将无法自动判断的数据写入问题清单；PostgreSQL 生效区间排他约束仅在数据清理完成后启用。

## 3. 当前文件职责判断

| 区域 | 当前判断 | 原因 |
|---|---|---|
| 生产拓扑 | 已完成基础文件拆分 | 标准作业、拓扑和产品路线已经有独立模型、DTO、服务和仓储文件；兼容聚合入口暂时保留 |
| 产品路线 | 基础生命周期已完成，修订复制待做 | `DRAFT/PUBLISHED/ARCHIVED` 的编辑、归档、删除保护已落地；路线家族和“复制为新修订”仍待后续实现 |
| 计件工价 | canonical 契约与基础服务已完成 | 仍需完成真实 PostgreSQL 迁移验收和历史问题清理 |
| 计件记录 | 快照服务和生产执行接入已完成 | 已稳定承接路线步骤、工价版本和金额快照；新增报工入口必须复用统一服务 |

拆分前的集中点（仅作历史记录，不代表当前文件仍承担这些职责）：

| 文件 | 约行数 | 当前混合职责 |
|---|---:|---|
| `server/services/production_service.go` | 历史聚合入口 | 当前主要保留事务服务兼容类型、公共错误和默认运行时依赖 |
| `server/services/production_dto.go` | 已删除的历史聚合 DTO | 当前 DTO 已分布到 `production_process_dto.go`、`production_topology_dto.go`、`production_route_dto.go` |
| `server/repositories/production_repository.go` | 兼容组合接口 | 具体查询、保存、删除和预加载已分布到三个生产仓储文件 |
| `server/services/piecework_service.go` | 班组与工价的兼容聚合服务 | 班组和工价规则已有独立服务文件 |
| `server/handlers/piecework.go` | 班组与工价的兼容 Handler 文件 | 班组和工价 Handler 已拆到独立文件 |
| `server/models/piecework.go` | 已删除的历史聚合模型 | 工价规则和计件记录已有独立模型文件 |

行数不是唯一拆分理由。真正的拆分依据是事务边界、生命周期和变更原因不同。

## 4. 推荐文件拆分

PR1 已按以下边界完成基础拆分。后续继续保持现有 Go package、数据库表名和外部入口稳定，不要同时把整个生产域迁入 `server/modules`，避免把目录迁移、行为修改和数据迁移混成一个批次。

```text
server/models/
├─ production_process.go          // ProcessStep
├─ production_topology.go         // ProductionLine、LineSegment
├─ production_route.go            // ProductionRoute、ProductionRouteStep
├─ piecework_rate.go              // PieceworkRate
├─ piecework_record.go            // PieceworkRecord
└─ team.go                        // 已独立，保持

server/services/
├─ production_process_service.go
├─ production_process_dto.go
├─ production_topology_service.go
├─ production_topology_dto.go
├─ production_route_service.go
├─ production_route_dto.go
├─ production_route_lifecycle.go
├─ piecework_rate_service.go
└─ piecework_team_service.go

server/repositories/
├─ production_process_repository.go
├─ production_topology_repository.go
├─ production_route_repository.go
└─ production_repository.go  // 兼容组合接口，暂不作为新业务的实现入口

server/handlers/
├─ production_topology_handlers.go  // 当前仍承载路线 Handler，后续可单独拆出
├─ piecework_rate_handlers.go
└─ piecework_team_handlers.go

server/routes/
├─ routes_production.go
└─ routes.go  // 当前 piecework 路由注册仍在此文件，后续可单独拆出
```

当前不应再往 `production_service.go`、`production_repository.go`、`production_topology_handlers.go` 或 `routes.go` 堆叠新的跨职责业务。已有兼容入口可以暂时保留给 Handler 调用，但新逻辑应分别落入对应的独立服务、仓储、DTO 和生命周期文件。`PieceworkRate` 与 `PieceworkRecord` 的独立仓储、计件记录服务、独立路线 Handler 和独立 piecework 路由文件属于后续整理项，不得在文档中写成已经完成。

前端计件应增加显式 API 契约与适配器：

```text
src/features/piecework/
├─ contracts/piecework-rate-api-dto.ts
├─ adapters/piecework-rate-api-adapter.ts
├─ data/piecework-rate.ts
├─ data/team.ts
├─ services/piecework-rate-service.ts
├─ services/piecework-team-service.ts
└─ components/rate-action-dialog.tsx
```

页面领域模型不能继续直接假设后端返回 `piecePrice`。后端 DTO、前端 API DTO 和页面模型之间必须显式转换。

## 5. 第一阶段暂时不要修改

- APS、委外、条码状态和生产执行服务：第一批只作为路线 ID 稳定性的回归验证方；
- `src/features/piecework/tabs/templates.tsx`：计件模板不是工价规则稳定身份的替代；
- 计件页面视觉结构：底层 DTO 和接口未统一前，不做大规模改版；
- `PieceworkRate`：机械拆分批次不新增业务字段；

## 6. 分阶段实施

### PR0：消除数据破坏风险（已完成）

1. 移除 `InitDB()` 常规启动路径中的 `prepareProductionTopologySchema()`；
2. 历史拓扑清理如仍需要，改成有版本标记、只执行一次、可审计的迁移；
3. 增加迁移测试或静态守卫，禁止常规启动执行 `DROP TABLE production_route_steps`；
4. 核对已有路线步骤，以及条码状态、执行记录、委外转移和检验中的孤儿 `routeStepId`。

验收：

- 连续启动服务两次，路线步骤数量、内容和 ID 完全不变；
- 已有路线和执行事实仍能解析对应步骤；
- 常规迁移日志没有删除路线步骤表。

### PR1：机械拆分职责，不改行为（已完成）

按第 4 节拆分文件和窄仓储接口，保持：

- 数据库表名、列名和 GORM package 不变；
- API 路径和 JSON 字段不变；
- 审计模块名和权限不变；
- 只移动代码和拆接口，不增加业务字段。

回归范围：

- 生产拓扑保存和版本冲突；
- 工段与作业项目动态绑定；
- 路线保存和引用校验；
- 作业项目保存；
- 班组 CRUD；
- 现有工价 GET/POST 行为快照。

验收：

- 拆分前后 API 和数据库行为一致；
- 拓扑服务不依赖路线仓储接口；
- 工价服务不与班组服务共用一个业务服务类型。

### PR2：保护作业和路线身份（已完成基础生命周期保护）

已完成文件：

- `server/services/production_route_service.go`
- `server/services/production_route_lifecycle.go`
- `server/repositories/production_route_repository.go`
- `server/handlers/production_topology_handlers.go`
- `server/services/production_route_lifecycle_test.go`
- `server/services/production_route_service_lifecycle_test.go`

已完成行为：

- 草稿路线可编辑，并可增加、替换和移除路线步骤；
- 发布路线不可原地修改；
- 发布路线只能原样归档；
- 归档路线只读；
- 已发布路线不能删除；
- 有下游生产事实引用的草稿路线不能删除；
- 新建路线和临时路线步骤由应用层补齐稳定 UUID，避免依赖数据库默认函数；
- 生命周期冲突通过 HTTP `409` 返回。

尚未完成：

- 发布后“复制为新修订”的 API、服务和页面流程；
- 路线家族 ID 与业务修订号的独立数据模型；
- 对 `ProcessStep`、`LineSegment`、`ProductionLine` 的完整引用删除保护。

目标生命周期：

```text
DRAFT
├─ 可编辑步骤
├─ 可删除
└─ 可发布

PUBLISHED
├─ 路线头和步骤不可原地修改
├─ 路线步骤不可删除
└─ 修改必须创建新修订

ARCHIVED
├─ 只读
└─ 继续供历史执行、追溯和结算引用
```

目标模型需要区分：

- 路线家族身份；
- 路线业务修订号；
- 当前记录的乐观锁版本；
- 每个修订下不可变的路线步骤 ID。

删除保护：

- 被工段映射或路线引用的 `ProcessStep` 优先停用，不直接删除；
- 被已发布路线引用的 `LineSegment` 不允许删除；
- 被执行、委外或工价事实引用的路线和步骤不允许删除；
- 归档路线仍保留全部步骤。

### PR3：统一计件工价契约（基础实现已完成）

已落地：

- `processStepId`、`routeStepId`、`effectiveFrom/effectiveTo` 和 `version` 进入 canonical command；
- `effectiveAt` 和 `piecePrice` 保留为读取投影/兼容边界，不进入 canonical PATCH；
- POST、PATCH、DELETE 路由和版本冲突响应已对齐；
- PATCH 强制 SDRTS `o/n`，旧字段被拒绝；
- 工价解析统一由路线步骤优先、标准作业回退的 resolver 承担；
- 启动迁移已支持旧数据回填、问题清单和 PostgreSQL 生效区间约束准备。

尚待完成：

- 真实 PostgreSQL 环境执行迁移并核对历史问题清单；
- 清理所有无法自动回填的旧工价后，再启用数据库非空和排他约束；
- 逐步下线内部旧模型写入口，保留兼容读取。

推荐合同：

```text
PieceworkRate
├─ id
├─ productId
├─ processStepId          // 必填，叶子作业
├─ routeStepId            // 可选，路线专属工价
├─ processCodeSnapshot
├─ processNameSnapshot
├─ unit
├─ unitPrice
├─ currency
├─ effectiveFrom
├─ effectiveTo
├─ status
├─ remarks
└─ version
```

匹配顺序：

```text
1. productId + routeStepId + 生效时间
2. productId + processStepId + 生效时间
3. 明确配置的默认规则
```

禁止：

```text
productId + segmentId
productId + 工段名称
productId + processName 自由文本
```

迁移步骤：

1. 新增可空的稳定 ID、生效区间和版本字段；
2. 将 `effectiveAt` 回填到 `effectiveFrom`；
3. 仅在 `processCode` 唯一匹配有效作业时自动回填 `processStepId`；
4. 无匹配或多匹配数据进入人工修复清单，不按名称猜测；
5. 回填完成后再将 `processStepId` 设为必填；
6. 增加生效区间重叠校验和数据库约束；
7. 同步实现 GET、POST、PATCH、DELETE 和版本冲突响应；
8. 前端通过 API adapter 对齐 `unitPrice`。

成型只有一个成型作业时，仍保存：

```text
productId = G24
processStepId = FORMING-OPERATION-ID
routeStepId = G24 路线成型步骤 ID（需要路线专属价格时）
```

不保存成型工段 ID 作为计价键。

### PR4：打通报工和计件记录（生产完工入口已接入）

已落地：

`PieceworkRecord` 从生产执行事实生成并冻结：

- `productId`；
- `routeId`、`routeStepId`、`processStepId`；
- 员工、班组和工作日期；
- 数量和单位；
- 命中的 `pieceworkRateId`；
- 单价、币种和金额快照；
- 来源执行记录 ID；
- 结算状态。

当前 `PieceworkRecordService` 已能根据工作日期解析工价，并冻结命中的 `rateId/rateVersion` 和金额快照。手工工序执行、扫码执行和委外验收复用的扫码路径已在 `COMPLETE + IN_HOUSE` 时进入同一事务 hook：有产品身份且命中有效工价时自动生成计件记录，未配置工价不阻断生产完工事实。后续新增报工入口必须复用该服务，不得自行计算工价。

工段只作为查询维度从路线步骤反查，不写成计价来源。

## 8. 批次 A、B 完成定义

1. 连续重启不会删除或重建已有路线步骤；
2. 生产拓扑、标准作业和产品路线拥有独立服务与仓储接口；
3. 班组、工价规则和计件记录不再混在同一服务或模型文件；
4. 工段与作业仍保持动态绑定，现有 API 行为不变；
5. 没有向计件页面或委外执行链提前增加未定义的跨域字段；
6. 后续每个业务改动都有明确文件归属和测试入口；
7. 发布路线不能原地修改、删除，归档路线保持历史步骤；
8. 草稿路线删除前会检查已存在的生产、条码和委外事实；
9. 生命周期冲突有服务错误、Handler `409` 响应和回归测试。
