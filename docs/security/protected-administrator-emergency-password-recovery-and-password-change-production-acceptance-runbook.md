# 受保护管理员应急密码恢复与改密上线验收规程

更新日期：2026-10-28。配套进度见 [实施与验收记录](authenticated-user-password-change-implementation-and-verification-progress.md)。本文描述待发布能力和操作要求，不代表已在生产执行。

## 适用边界

仍记得当前密码的用户通过头像菜单“修改密码”操作。具备账号管理权限的管理员可重置其他普通账号；受保护管理员遗失密码时，使用本文的离线维护命令。

恢复命令只允许已存在、未删除、状态为 active 的受保护管理员：账号名为 admin，或同时标记为受保护账号且使用 admin 权限预设。不创建、激活账号或补权限，也不为普通账号提供绕过后台授权的恢复通道。

执行资格来自服务器、容器和数据库的运维访问控制；`--operator` 和 `--reason` 是审计记录，不能代替运维身份认证、工单审批或身份核实。恢复功能没有 HTTP 接口，不需要知道旧密码，也不签发登录凭证。

## 一、操作前准备

1. 核实账号归属、请求人身份和恢复原因，记录工单、实际执行人和复核人。账号遭入侵时，先按事件处置流程限制访问。
2. 安排维护窗口，确认数据库备份及恢复演练记录。已有生产备份脚本及路径见 [VPS 运维手册](../ops/hostinger-vps-docker-runbook.md#11-备份与恢复)。本工具不自动备份。
3. 确认所有 API 实例已升级至支持 `password_version` 的代码，并已完成数据库迁移；旧实例仍可能接受旧凭证。不得通过恢复工具触发迁移。
4. 使用包含 `/app/recover-protected-administrator-password` 的同版本 API 镜像。核对 Compose Project、镜像摘要和数据库环境。不要打印容器环境变量、完整数据库连接字符串或整个生产 Compose 渲染结果。
5. 准备可交互的安全终端，关闭输入录制和可能捕获密码的调试工具。新密码只在隐藏输入提示后输入，不放进命令行、环境变量、文本文件、管道、聊天、工单或日志。

修改 `INITIAL_ADMIN_PASSWORD` 只影响首次建库，不会恢复已存在账号。不要用历史清理命令、删除账号重建或直接 SQL 写入明文密码替代本流程。

## 二、获取账号 ID 并执行只读预检

以下示例对应仓库 `compose.prod.yml` 的 `erp` Project，应在已配置生产环境的运维目录执行。示例中的占位符必须替换为已核实的非敏感元数据，不能填入密码。若环境通过 Hostinger Docker Manager 管理，应使用相同 Project 环境运行命令，不另写连接凭据到仓库。

尚不知道账号 UUID 时，允许通过受控数据库会话只读查询下列字段。不要查询 password 列：

```sql
BEGIN READ ONLY;
SELECT id, username, status, is_protected, permission_preset_id, password_version
FROM users
WHERE deleted_at IS NULL
  AND (LOWER(username) = 'admin'
       OR (is_protected = TRUE AND LOWER(permission_preset_id) = 'admin'));
COMMIT;
```

确认目标后，执行默认只读命令：

```bash
docker compose -p erp -f compose.prod.yml run --rm --no-deps -T app \
  /app/recover-protected-administrator-password \
  --user-id '<核实后的账号UUID>'
```

只读输出包含数据库主机、端口、数据库名、账号 ID、账号名和当前密码版本，以及 `READ ONLY` 标记。预检连接启用 PostgreSQL `default_transaction_read_only`，数据库层也拒绝写入；不会选择密码哈希、更新账号、写审计、运行迁移或创建默认数据。

记录当前密码版本，复核输出目标确为本工单账号。数据库配置只读取继承的 `DATABASE_URL`，不加载本地 `.env`，没有开发数据库或默认连接回退。数据库连接错误只输出脱敏说明。

本地从源码构建的命令入口位于 `server/cmd/recover-protected-administrator-password`；在 server 目录执行 `go run ./cmd/recover-protected-administrator-password --help` 可查看参数。

## 三、交互恢复

在真实终端执行，保持交互输入和 TTY；不要使用 `-T`、stdin 重定向或 `echo 密码 | ...`：

```bash
docker compose -p erp -f compose.prod.yml run --rm --no-deps app \
  /app/recover-protected-administrator-password \
  --user-id '<核实后的账号UUID>' \
  --apply \
  --expected-password-version '<只读预检得到的版本>' \
  --operator '<实际运维人员身份>' \
  --reason '<工单号及已核实的恢复原因>'
```

命令再次显示数据库及账号信息，要求输入精确确认文本：

```text
RECOVER <账号UUID> VERSION <预期密码版本>
```

确认目标后，在两个隐藏输入提示中输入新密码。规则与自助改密一致：至少 8 个字符，包含小写字母和数字，不超过 72 个 UTF-8 字节，首尾没有空白。前缀 `$2a$`、`$2b$`、`$2y$` 不接受为明文密码。输入不一致、当前密码相同、确认错误或输入中断均不会更新账号。

事务在行锁下重新检查账号资格、原密码哈希和预期版本。成功时同时完成密码哈希更新、`password_version + 1` 及 `PASSWORD_RECOVERY` 审计；任一步失败都回滚。审计记录实际填报操作人、工单原因、恢复操作 ID 和前后版本，不含密码和哈希。命令不会自动重试。

看到 `RECOVERY COMMITTED` 后，记录操作 ID 和新版本，再进入验收。命令会清除可控的密码字节缓冲区；Go 运行时中的字符串复制不提供完全清零保证，操作后让短生命周期命令退出。

## 四、异常处理与结果核对

| 现象                            | 处理                                                                   |
| ------------------------------- | ---------------------------------------------------------------------- |
| 要求交互终端                    | 从真实终端执行；容器保留 TTY，不通过文件或管道输入密码                 |
| 账号不符合资格                  | 复核 UUID、删除/停用状态和保护规则；本命令不绕过停用或调整权限         |
| 密码版本已改变                  | 停止原计划，重新只读预检并核对发生的账号变更，重新确认后才决定是否恢复 |
| 密码规则或二次输入错误          | 账号保持原样，重新开始并使用符合规则的密码                             |
| 数据库/审计失败、超时或连接中断 | 不能仅凭错误消息断言未提交；先查询账号版本和审计记录，再决定下一步     |
| 输出失败但提示可能已提交        | 同样按版本和审计核对，避免再次重置用户已收到的新密码                   |

可在只读数据库会话检查账号版本及目标的 `PASSWORD_RECOVERY` 审计，使用操作 ID 定位；不要查询密码或整个未脱敏错误上下文。成功审计与密码修改同事务，但连接在提交结果传回前中断时，调用方仍可能不知道结果。

不要为撤回一次密码恢复而还原整个业务数据库。灾难恢复如恢复了旧账号版本，可能让旧 JWT 重新有效；此时必须另行评估全节点 JWT 密钥轮换及业务数据恢复计划。

## 五、恢复后的账号验收

1. 使用新密码登录，确认账号 ID、身份和原权限正确，普通业务只读页面可访问。
2. 确认原密码无法登录；恢复前保存的 Bearer、登录 Cookie、WS 票据都被服务端拒绝。
3. 恢复前已有 WS 连接按版本检查关闭。空闲检查每 15 秒一次，还需考虑查询和写入超时；已通过认证正在执行的 HTTP 操作不会被撤回。
4. 由账号持有人通过头像入口再自行设置其独占的新密码，验证此后的再次登录。系统当前没有管理员重置后自动强制首次改密能力，这一步由操作流程落实。
5. 核对成功审计、操作 ID、版本变化及日志脱敏后关闭工单，撤销临时维护权限。

## 六、改密功能生产发布验收表

2026-10-28 已补本地隔离联调：两个以完整入口启动的 release API 共享临时 PostgreSQL/Redis，两个独立 Chromium 上下文通过不同代理连接，验证了管理员和无业务权限普通账号的头像改密、错误旧密码保留登录、旧 Bearer/Cookie 跨实例失效、旧 WS 以 1008 关闭及新密码登录。实际暂停 Redis 时改密约 2 秒返回 503，数据库版本/审计不变；恢复后成功。代理伪造头及最近未受信跳点已有自动回归。具体证据和边界见[实施与验证进度第四轮](authenticated-user-password-change-implementation-and-verification-progress.md#第四轮隔离双实例与真实浏览器联调)。这些结果不能替代下表的生产 HTTPS、代理链、真实设备、容量与时钟验收。

完整生产镜像构建已尝试，因 Docker Hub 连接超时未获取 Go/Rust 基础镜像元数据，尚不能确认完整镜像构建成功。发布前须在网络可用的构建环境重新构建、检查 API 与恢复命令均包含在产物中，记录镜像摘要后再执行生产验收；本地构建成功的独立二进制不能替代这一步。

日志验收须覆盖每一层。API 访问日志已对查询参数中的票据、令牌、密码等凭证字段脱敏，并清除 Referer 的用户信息和片段；当前 Docker Web Nginx 的访问日志不记录查询串，Referer 固定省略。**Nginx 错误日志、外层网关、Cloudflare 和其他代理不受 API 脱敏控制**，失败握手/上游故障时尤其需要检查。在日志持久化前配置相同脱敏，限制日志访问及保留时间，不开启含请求头/请求体的调试采集。仍采用旧式主机 Nginx 模板的环境还须替换其继承的 combined 访问日志格式。已有日志不会被代码追溯清理，若发现有效凭证，应按泄露处置并撤销相应会话；WS 票据单次使用、短 TTL 不能代替脱敏。
