# 状态码治理第六阶段整理审计

## 一、审计背景

消息中心业务事件源状态码治理已连续落地以下能力：

- 第三阶段：安全重命名
- 第四阶段：批量 rename 冲突建模
- 第五阶段：后端原子事务接口

功能链路已经形成，但结构层面开始出现以下风险：

- 文件职责扩张
- 过渡性逻辑累积
- 前后端数据契约分叉
- 后续扩展复杂度快速上升

本次审计只聚焦消息中心业务事件源状态治理主链路，不扩展到全仓清理。

## 三、职责地图（当前状态）

### 1. UI 编排层

#### `business-event-source-card.tsx`
当前承担的职责明显偏多，至少包括：

- 卡片展示状态管理
- 分区保存协调
- 状态 rename 分析触发
- batch blocker / warning 保存前判断
- 原子事务 payload 组织
- 事务成功后 source / rules 双回写
- optimistic committed state 协调

结论：
该文件已经不只是 UI 容器，而是同时承担了 UI orchestration 与 transaction orchestration。

### 2. 通用分区保存动作层

#### `business-event-source-card-actions.ts`
职责相对清晰：

- 全量保存
- 分区保存
- 分区撤销
- optimistic committed patch 应用

问题：
`statuses` 分区目前已分叉出专用原子事务路径，导致：

- 通用 section save 仍负责多数分区
- `statuses` 又在卡片文件内走专用提交流程

结论：
这里已经出现“通用保存框架”和“状态专用保存框架”并存的双轨迹象。

### 3. 状态领域层

#### `business-event-source-status-model.ts`
职责清晰：

- 状态草稿增删改移
- 状态摘要

#### `business-event-source-status-safe-rename.ts`
当前同时承担：

- rename draft 收集
- 单状态 rename 安全分析
- batch rename 冲突分析
- rules 迁移结果计算

结论：
这是一个明显的领域层核心文件，但职责已从“安全改名分析”扩展到“分析 + 迁移计划生成”。

### 4. 历史补偿事务辅助层

#### `business-event-source-status-transaction.ts`
当前只剩：

- rollback target 计算
- 失败消息拼装
- 基于快照替换 rules

审计结果：
主链路检索后，该文件当前已不再被生产路径直接引用，仅剩测试引用。

结论：
该文件已从“主链路事务辅助”降为“历史补偿事务遗留辅助”。

### 5. 前端协议层

#### `routing-service.ts`
职责：

- 对接后端 API
- 请求发送
- 反序列化响应

问题：
同一 service 中同时承载：

- 旧通用 `updateEventSource`
- 新专用 `commitEventSourceStatusRenameTransaction`

结论：
协议层本身还算清晰，但 status rename 已经形成专用协议分支。

### 6. 后端通用 DTO / 通用编辑接口

#### `business_event_source_dto.go`
职责：

- business event source 通用 DTO
- request/response 映射
- config 级校验

问题：
状态 DTO 仍要求：

- `label`
- `phase`
- `isTerminal`
- `defaultResolve`

#### `business_event_source_service.go`
职责：

- 通用 event source CRUD
- immutable 约束

结论：
通用后端接口仍代表旧的完整状态对象语义，不代表前端已经收口后的 `code-only` 状态模型。

### 7. 后端专用事务层

#### `business_event_source_status_transaction_service.go`
职责：

- 状态 rename 专用请求/响应
- persisted 状态 rename 校验
- 批量 rules 迁移
- event source + rules 原子提交

问题：
该文件内部既有：

- 请求 DTO
- 校验
- 领域分析
- 规则迁移
- 事务编排
- 响应组织

结论：
虽然当前实现集中有利于快速落地，但长期看职责密度偏高。

## 四、冗余点清单

### A. 已进入“可清理候选”的内容

#### 1. `business-event-source-status-transaction.ts`
现状：

- 当前生产主链路已切到后端原子事务
- 该文件当前只剩测试使用

判断：
- 若不再需要前端补偿事务 fallback，则可进入删除候选
- 若需要保留历史降级能力，则应明确标为 fallback-only helper

#### 2. `applyBusinessEventStatusRenamesToRules()` 的角色需要重新定义
现状：

- 当前仍被卡片保存流用于计算 `affectedRules`
- 但它已不再承担“最终提交 rules 更新”的主职责

判断：
它应更明确地收口为：

- 迁移计划构造辅助
- affected rules 推导辅助

而不是继续保留“前端主迁移执行器”的语义影子。

### B. 已出现双轨的内容

#### 1. `statuses` 分区保存
当前存在两套保存语义：

- 通用 section save
- 状态 rename 专用事务 save

这不是 bug，但已经需要显式分层，否则卡片层会持续膨胀。

#### 2. 后端 event source 更新协议
当前存在两套契约：

- 通用 event source update DTO
- status rename 专用 transaction DTO

这也是合理演进结果，但需要明确文档化“谁是兼容层，谁是主链路”。

## 五、数据合规审计

## 1. 当前最显著的数据契约分叉

### 前端状态模型
`business-event-source-types.ts` 中：

- `BusinessStatus` 只包含：
  - `id`
  - `order`
  - `code`

这是当前前端主链路的 authoritative 表达。

### 后端通用 DTO
`business_event_source_dto.go` 中：

- `BusinessStatusDTO` 包含：
  - `id`
  - `order`
  - `code`
  - `label`
  - `phase`
  - `isTerminal`
  - `defaultResolve`

这说明：

- 前端主模型已经认为状态是 `code-only`
- 后端通用协议仍认为状态是“完整语义对象”

这就是当前最大的合规风险。

## 2. 当前真实结构结论

### authoritative source
当前更接近以下事实：

- 前端展示与编辑主语义：`business-event-status-catalog.ts`
- 前端状态持久化主输入：`code-only`
- 后端通用存储层：仍保留旧语义字段

### compatibility-only 字段
在当前链路下，以下字段更像兼容负担，而不是前端编辑权威输入：

- `label`
- `phase`
- `isTerminal`
- `defaultResolve`

## 3. 当前合规风险评级

### 高风险
- 前后端长期双契约并存，后续 mixed rename + add/delete 扩展时会显著抬高复杂度。

### 中风险
- 新事务接口与旧通用更新接口分别依赖不同状态语义，若后续继续拓展功能，可能导致行为不一致。

### 低风险
- 当前第五阶段已通过专用事务 DTO 避开旧通用 DTO，短期功能风险可控。

## 六、长期结构建议

## 建议目标结构

### 前端

#### 1. `status-domain/*`
承载：

- rename draft collection
- rename plan analysis
- batch conflict analysis
- affected rules planning

#### 2. `status-transaction/*`
承载：

- transaction payload builder
- transaction result reconciliation
- frontend optimistic state adapter

#### 3. `business-event-source-card.tsx`
只保留：

- UI 交互
- 用户提示
- 调用上层 action

不再直接承载过多 transaction 编排细节。

### 后端

#### 1. 通用 source service
保留：

- CRUD
- immutable 保护
- 默认种子与通用 DTO

#### 2. status rename transaction service
拆成更明确的子职责：

- request validation
- rename analysis
- rule migration planner
- transaction executor

#### 3. shared validation helpers
例如：

- rule reference validation
- derived approval action validation

## 七、建议执行顺序

### P1：低风险职责收口
优先做：

- 标定 `status-transaction.ts` 的角色，并决定删除或降级为 fallback/test-only
- 将卡片中的 status transaction payload 组装与结果回写逻辑抽离

### P2：主链路命名与语义收口
优先做：

- 重新命名 `applyBusinessEventStatusRenamesToRules()` 的职责表述
- 明确它是 planning helper，而不是提交执行器

### P3：数据合规专项
优先做：

- 给 status 字段做 authoritative / compatibility-only 分级
- 明确后端通用 DTO 的未来策略：继续兼容、逐步收口，还是拆分层次

### P4：长期文档落地
补齐：

- 主链路职责图
- 数据契约说明
- mixed rename + add/delete 的后续演进方案

## 八、第一轮结论

当前最值得优先处理的，不是立刻删很多文件，而是先做三件事：

- **收口 `business-event-source-card.tsx` 的 transaction orchestration 职责**
- **处理 `business-event-source-status-transaction.ts` 的去留**
- **正式定义前后端 status 数据契约中的 authoritative source 与 compatibility-only 字段**

如果这三件事先做对，后续再做冗余删除和 mixed 场景扩展，风险会低很多。
