# MRP 需求分析重构复盘

日期：2026-04-09  
范围：`src/features/mrp/**` 与原 `src/features/trading/**` 下承载 MRP 需求分析的迁移与拆分

## 1. 复盘目标

这份复盘不是为了把“代码变短了”包装成一次成功重构，而是为了回答四个更实际的问题：

1. 本轮到底解决了哪些真实痛点。
2. 这次拆分后，代码边界是否真的更清晰了。
3. 当前收益是已经落地的，还是只是未来可优化空间。
4. 还有哪些历史耦合没有彻底清掉，后续应该怎么收口。

本文结论基于当前工作区代码现状，不以主观印象为依据，也不把尚未完成的优化写成既成事实。

## 2. 本轮重构范围

本轮重构主要覆盖两条主线：

1. 将 MRP 需求分析相关的数据、服务、Hook、页面入口从 `trading` 语义中抽离，收口到 `src/features/mrp`。
2. 将需求分析列表从“大容器 + 大表格 + 大量行级判断”的实现方式，拆分为更清晰的容器组件与行级组件。

当前可见的结果包括：

- `src/features/mrp/index.ts` 已作为模块出口统一导出 data、hooks、services、pages。
- 原先位于 `src/features/trading/` 下的 `requirement-schema.ts`、`use-requirements.ts`、`use-mold-status.ts`、`requirement-service.ts`、`requirement-core-service.ts`、`requirement-export-service.ts` 已迁移到 `src/features/mrp/`。
- `part-requirements.tsx` 已通过 feature-local 方式直接组合 `SelectionTree`、`RequirementDrawer` 与 `useRequirements`，不再由 `trading` 页面层承载 MRP 需求分析页本身。
- `requirement-list.tsx` 已拆分出 `requirement-row.tsx` 与 `supply-analysis-details.tsx` 两个更细颗粒度组件。

## 3. 重构前的真实问题

## 3.1 领域边界模糊：MRP 长期寄生在 Trading 语义下

在重构前，需求分析虽然业务语义上属于 MRP，但其 schema、Hook、service 却长期挂在 `src/features/trading/` 下。这会带来三个问题：

1. 职责误导。开发者会自然认为这部分逻辑属于 Trading，而不是独立的 MRP 能力。
2. 依赖扩散。后续任何页面、导出、统计、权限接入，只要复用这条链路，都容易继续从 `trading` 引用，形成历史路径依赖。
3. 迁移成本持续累积。一旦后面要做独立路由、独立权限、独立 PDA 端适配，所有引用路径都需要重新梳理。

这类问题的危险不在于“代码能不能跑”，而在于领域边界长期错误后，会把后续每一次迭代都拖进错误的模块中。

## 3.2 上帝组件问题：列表容器承载过多职责

`requirement-list.tsx` 在本轮之前属于典型的上帝组件风险点。一个列表容器同时承担：

- 搜索输入状态；
- 缺料筛选状态；
- 分组计算；
- 折叠状态管理；
- 表头结构；
- 行级渲染；
- 供需分析细节展示；
- 缺料提示、包装信息、状态文案等多处条件渲染。

这种结构的直接后果不是“文件长得不好看”，而是：

1. 修改任何一个局部规则时，都需要先理解整块表格上下文。
2. 搜索、筛选、折叠这类容器状态变更，会驱动大块视图一起重新进入渲染流程。
3. 行级展示逻辑很难被单独复用，也不利于后续做局部测试或性能优化。

## 3.3 展示逻辑与业务语义交错

需求分析表并不是普通表格，它混合了大量业务语义：

- `effectiveGap > 0` 时的缺料判定；
- 包装换算的正反向公式展示；
- 可用库存 = 库存 - 锁定 的提示语义；
- 在途采购、WIP、总供给等桶位解释；
- “待备料 / 已就绪”的状态映射。

当这些逻辑全部写在同一个大组件里时，开发者在改 UI 时很容易误伤业务含义，在改业务规则时也很容易牵动布局结构。

## 3.4 可复用性和测试切入点不足

如果一个列表组件既负责容器逻辑，又负责所有单元格细节，那它几乎没有可独立复用的单元。后续如果要：

- 把某一行显示逻辑搬到移动端；
- 做一个更紧凑的卡片式需求分析视图；
- 针对供需分析做独立单测或快照测试；

都会面临“只能从大组件里硬拆”的问题。

## 4. 本轮采取的重构动作

## 4.1 将 MRP 的事实源收口到独立模块

本轮最重要的变化，不是单个组件拆分，而是事实源归位：

- `data` 收口到 `src/features/mrp/data/requirement-schema.ts`
- `hooks` 收口到 `src/features/mrp/hooks/`
- `services` 收口到 `src/features/mrp/services/`
- 页面入口落到 `src/features/mrp/pages/part-requirements.tsx`
- 模块出口统一由 `src/features/mrp/index.ts` 管理

这一步的价值在于，后续任何与需求分析相关的变更，都有明确落点，不需要再去 `trading` 中“猜”哪一部分才是 MRP 自己的代码。

## 4.2 页面层只做编排，不再吞并细节实现

`part-requirements.tsx` 现在承担的是页面编排角色：

- 通过 `useRequirements()` 获取活动订单、分析结果、统计和计算动作；
- 维护 `selectedKeys` 与抽屉开关；
- 组织 `SelectionTree` 和 `RequirementDrawer` 的交互。

这种结构说明页面层已经开始回归“容器页”的职责，而不是继续向下吞并服务调用和局部业务细节。

## 4.3 将列表职责下放到行组件

当前 `requirement-list.tsx` 已经明显收敛为容器组件，主要保留：

- 搜索状态；
- 缺料过滤状态；
- 分组与折叠状态；
- 分组头部与表头骨架；
- 对 `RequirementRow` 的映射。

行级职责则下放到了 `requirement-row.tsx`：

- 物料编码、名称、规格显示；
- 总需求、可用库存、有效缺口的展示；
- 包装单位和状态提示；
- 缺料高亮与文案映射。

这意味着后续修改“缺料红色高亮”或“包装换算文案”时，开发者已经不需要在整个列表容器中人肉检索。

## 4.4 将供需分析细节进一步抽离

`supply-analysis-details.tsx` 单独承接了库存桶位展示与总供给解释：

- 库存、锁定、在途采购、WIP 四类 bucket；
- tooltip 中的解释公式；
- 总供给汇总视图。

这是一次很有价值的“二次下放”。因为它把行组件里最容易继续膨胀的一块复杂视图提前切开了，避免 `RequirementRow` 重新演化成下一个上帝组件。

## 5. 当前已经获得的收益

## 5.1 代码职责边界更清晰

当前结构下，职责分层已经比较明确：

- `PartRequirements` 负责页面编排；
- `RequirementDrawer` 负责承载分析结果弹层；
- `RequirementList` 负责容器状态、筛选、分组；
- `RequirementRow` 负责单行渲染；
- `SupplyAnalysisDetails` 负责供需分析细节呈现。

这比“一个组件里放所有逻辑”更接近可持续迭代的状态。

## 5.2 维护成本已经实际下降

这次收益并不是抽象层面的。以一个高频修改场景为例：

- 如果需要修改缺料颜色、文案、包装提示，现在主要落点在 `requirement-row.tsx`。
- 如果需要调整供需分析 bucket 或 tooltip 文案，现在主要落点在 `supply-analysis-details.tsx`。
- 如果需要新增筛选项或优化分组逻辑，现在主要落点在 `requirement-list.tsx`。

开发者可以更快定位改动位置，也更容易评估影响面。

## 5.3 为性能优化创造了真实落点

这里需要刻意区分“已经提升”与“更容易提升”：

本轮拆分后，列表性能优化的切入点已经清晰了，但不能直接宣称性能问题已经彻底解决。当前搜索与筛选变化时，`RequirementList` 仍会重新执行过滤与分组，并重新映射可见行。

不过与重构前相比，现在已经具备了继续优化的基础条件：

1. 可以对 `RequirementRow` 做 `React.memo` 或更细粒度的 props 稳定化。
2. 可以对搜索输入引入 `useDeferredValue`，降低输入抖动对大表格的影响。
3. 如果后续数据量继续增长，可以在 `RequirementList` 层引入虚拟滚动，而不需要先拆碎整块表格。

也就是说，本轮并非“性能收官”，而是完成了性能治理前置工程。

## 5.4 复用能力明显增强

现在最直接可复用的单元已经形成：

- `RequirementRow` 可以作为桌面表格、精简列表、导出预览等视图的基础单元；
- `SupplyAnalysisDetails` 可以在未来的物料详情页、采购建议卡片、移动端明细页中复用；
- `useRequirements` 可以继续作为页面编排层之上的查询/计算入口。

这类复用不是简单复制 JSX，而是复用已经包含业务语义的稳定单元。

## 6. 本轮没有彻底解决的问题

## 6.1 本地化命名空间已完成归一，但仍需持续守边界

本轮已将需求分析相关文案从 `trading.requirements.*` 彻底归一到 `mrp.requirements.*`，不再保留兼容层或旧 key 映射。

这一步带来的直接收益是：

1. 代码目录与本地化语义终于对齐。
2. MRP 模块不再借用 Trading 命名空间承载自身能力。
3. 页面、组件、导出服务、命令菜单入口都可以直接从 key 判断功能归属。

后续需要继续约束新增文案，避免再次把 MRP 语义写回 `trading.*`。

## 6.2 `useRequirements` 仍依赖 Trading 销售订单事实源

当前 `useRequirements.ts` 仍通过 `@/features/trading/sales` 的 `getSalesOrders` 读取活动订单，同时监听：

- `xdfc_trading_updated`
- `xdfc_sales_orders_updated`

这说明 MRP 页面虽然已独立，但上游事实源仍来自销售订单域。这本身不一定是错误，因为 MRP 确实要依赖销售订单触发需求计算；问题在于这种依赖目前仍是直接依赖 Trading 实现，而不是通过更明确的领域契约来接入。

换句话说，MRP 已经从“代码归属”层面独立了一步，但还没有完全实现“上游依赖隔离”。

## 6.3 列表性能优化尚未最终落地

当前 `RequirementList` 中的 `useMemo` 已经用于过滤和分组，但仍有几个现实点需要正视：

1. 搜索时会对整个数据集执行 `filter + group`。
2. `RequirementRow` 目前未做 `memo`。
3. 表格仍是全量渲染，不是虚拟列表。

因此，如果后续需求分析数据量继续显著增长，这部分仍可能出现交互迟滞。本轮解决的是结构问题，不是所有性能问题。

## 6.4 行组件内部仍混合了部分显示规则

`RequirementRow` 相比之前已经清晰很多，但它仍同时承担：

- 缺料态显示；
- 包装换算文案选择；
- 状态标签映射；
- 来源订单数量提示。

这在当前阶段是合理的，因为这些都是“单行语义”。但如果后续继续往行内堆更多采购建议、交期提醒、替代料信息，`RequirementRow` 仍有再次膨胀的风险，需要提前警惕。

## 7. 这次重构最重要的判断

本轮并不是一次“纯 UI 美化重构”，而是一次有明确方向的架构收口：

1. 从目录归属上，把 MRP 从 Trading 中拉出来。
2. 从页面编排上，让页面层只做容器协调。
3. 从列表结构上，把上帝组件拆成可理解、可复用、可继续优化的单元。

因此，这次工作的价值不应该只按“少了多少行代码”来衡量，而应该按“以后修改需求分析是否更安全、更便宜、更容易扩展”来衡量。

从这个角度看，本轮重构是有效的，而且方向正确。

## 8. 建议的下一步

## 8.1 坚持单一命名空间

后续所有需求分析新增文案、导出字段、提示语、菜单标题，都应直接落在 `mrp.*` 下，不再接受回写 `trading.requirements.*`、补丁 key 或兼容映射。

## 8.2 补齐性能治理

按优先级建议继续推进：

1. 为 `RequirementRow` 评估 `React.memo` 的收益。
2. 为搜索输入引入 `useDeferredValue` 或受控防抖。
3. 当数据规模继续增长时，引入虚拟滚动。

## 8.3 为业务规则提取纯函数或 view-model

将以下逻辑逐步从 JSX 条件分支中抽出：

- 缺料状态映射；
- 包装公式文案选择；
- 供需桶位格式化；
- 状态标签文案映射。

这样可以降低视图层中的业务判断密度，也有利于测试。

## 8.4 补充最小回归测试

建议优先覆盖四类行为：

1. 搜索与缺料筛选是否正确。
2. 分组折叠状态是否正确。
3. `effectiveGap` 不同取值下的行级状态是否正确。
4. 包装信息与供需分析 tooltip 是否按预期显示。

## 9. 结论

本轮 MRP 需求分析重构已经完成了两件真正有价值的事情：

1. 把 MRP 相关事实源从 `trading` 目录中收口到独立模块，为后续独立演进打下基础。
2. 把 `requirement-list` 这类高风险上帝组件拆成更清晰的容器、行级视图和供需分析子组件，使维护、复用和后续性能优化都有了明确落点。

同时也要保持判断克制：

- 这轮不是彻底完成了 MRP 独立化；
- 也不是已经完全解决了大表格性能问题；
- 它完成的是最关键的一步：先把结构做对，再让后续优化变得可做、可控、可持续。
