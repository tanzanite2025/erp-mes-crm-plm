# 品质标准自定义偏差等级与实测留痕

2026-11-09 检验站与扫码位置确认：品质标准中的“环节”统一指品质所属的检验站，系统默认写入成型检验站、机加检验站、精细检验站、涂装检验站，并允许配置。四站也是实际扫码的地点，扫码发生在相应站点转往下一环节的阶段。内部结构为“检验站 → 重量项目 → 等级规则”；品检站 ID、生产路线节点 ID、工序 ID 分别表达，扫码业务可引用品检站身份。当前已实现目录及规则配置，四站扫码录入与流转不能视为已经接通。

## 使用入口

- 品质管理 → 品质操作手册 → 如何建立品质标准：按准备资料、添加项目、配置等级、保存核对、审批发布五章阅读。
- 品质标准列表 → 新增受控协议：每个检验项目独立配置等级名称、数量、上下允许偏差及合格/不合格判定。
- 草稿或已驳回标准 → 检验规则编辑：统一使用三级编辑器，不依赖标准编号或产品字段切换编辑模式。
- 品质检测 → 录入检测，或待检任务 → 录入检测：选择产品匹配的已发布标准、填写批次及实测值，由服务端判定。已完成任务提供“查看实测记录”。

## 规则属于标准项目

`items[].gradingMode = DEVIATION_BANDS` 使用如下等级结构：

```json
{
  "level": "优",
  "lowerTolerance": 1,
  "upperTolerance": 2,
  "result": "PASS"
}
```

每项配置 1–20 个等级，名称不为空、忽略大小写不重复、最长 40 个字符。上下偏差为非负有限数，按从严到宽的顺序分别严格递增。不合格等级之后不能配置合格等级。

等级是围绕中心值的嵌套范围，服务端按列表顺序取首个匹配项；范围端点包含在内，已匹配的较严等级不再落入后续等级。首个等级可以有范围，两侧允许不对称。例如中心值 450 G，“优”允许 −1/+2 G，“可接受”允许 −5/+8 G：449、452 属于“优”，445、458 属于“可接受”。

服务端使用十进制有理数比较已解析的数值，避免 `0.3 - 0.1` 的二进制浮点误差把端点错误判为超限。无法表示的中心值与偏差组合会被拒绝。

S/A/B 只是新建时可修改的默认值。执行计算不依赖固定名称，也不读取全局可变等级目录。不同产品、不同项目的规则互不覆盖。

## 品质规则与生产集中录入的对齐边界（2026-11-09）

具体产品品质标准的重量规则编辑已按“检验站 → 重量标准项目 → 等级规则”组织。检验站是品质所属的品检站点，标准按站组织项目；中心值、单位和 `levels` 继续归项目持有，同一检验站下不同项目的规则独立，移动项目所属检验站不会替换等级。新增、编辑和详情复用相同的三级结构。当前仅收口内部配置，路线、扫码及报警不自动进入实施；验收记录以[检验站配置文档](quality-standard-configurable-inspection-stage-catalog-and-item-name-snapshots.md)的“逐项对齐顺序与验收”为准。

重量标准维护与服务端判定归品质侧，四个品检站同时也是实际扫码地点，在相应站点转往下一环节时扫码录入。产品跟踪单中的生产工序信息仍由相应来源业务维护；扫码录入引用已发布标准版本及重量项目，调用同一套品质判定能力。卷制、组合、成型完成后可以一次录入三个已完成工序的分区，不能按条码当前 `routeStepId` 把填写范围缩成一个当前工序，也不能据此将四站改写成站外的单一转录点。完整职责见[检验站配置文档的职责边界](quality-standard-configurable-inspection-stage-catalog-and-item-name-snapshots.md#品质规则与生产录入的职责边界2026-11-09)。

本文下方描述的是已实现的通用实测契约：前端和后端均以整份标准的项目集合核验必检项，用户确认保留现有校验。四站扫码定位产品跟踪单、引用产品及标准版本、录入各扫码点需要的信息，尚需按实际流程逐项对齐；引用的产品、标准版本、项目须由服务端核验，不能只在界面隐藏项目来绕过现有必检校验。

用户进一步确认：机加、精细、涂装等现场工作完成后，人员先人工书写记录，现场环境不便拿手机；四个品检站本身就是扫码地点，扫码发生在相应站点转往下一个环节的阶段。不能把人工书写理解成全部数据要在四站以外另找地点事后录入。正式提交时要求必检数据齐全是正确行为，不列为分站提交缺口，不据此修改现有校验。各扫码点具体录入哪些跟踪单信息、后续去向如何核验，尚需逐项对齐，不能自动推导填写范围。实际检验人员及检验时间与系统录入账号、录入时间分别表达；现有 `Inspector` 与 `CompletedAt` 来源于提交账号及服务器提交时间。完整说明见[现场人工记录与系统录入的边界](quality-standard-configurable-inspection-stage-catalog-and-item-name-snapshots.md#现场人工记录与系统录入的边界)。

现有服务端数值判定、规则快照、提交防重和不合格异常记录已有基础；生产扫码集中录入与规则引用的完整连接尚未实施。现场先手工填重量，后续自动读秤仅作为生产侧另一种输入来源。超差提示依赖服务端 `FAIL` 结果，不以“未达到 S 级”代替不合格判定；报警、处置和过站分别对齐，不由规则判定直接改写生产状态或决定报废。

## 实测提交与事务边界

`POST /quality/tasks` 接收标准 ID、当前版本、产品、批次和 `inputData.measurements`；每项实测包含 `itemId`、`value`、`unit`。界面不提交等级或合格结果；客户端携带结果时，服务端仍重算并覆盖。

同一事务内执行以下操作：

1. 核对当前检验人员，锁定已有任务，验证领取人及未完成、未取消状态。保持已有产品、标准、批次和生产来源关联，拒绝改绑。
2. 对标准加共享锁，要求已发布、产品一致、客户端版本与当前版本相同。
3. 校验项目唯一性、必检项、实测数值、单位及等级规则，拒绝未知或重复项目。当前执行器统一使用项目中心值和上下允许偏差进行数值判定。
4. 计算逐项等级和总结果，规范化实测输入，写入标准版本、规则快照、逐项结果、完成人员和完成时间。
5. 不合格时创建待处置异常，写入审计。任一步失败，整笔事务回滚。

界面为每次录入生成 `submissionKey`，失败重试复用该值。数据库以可空唯一列保存提交标识，PostgreSQL 事务锁串行处理相同标识。相同人员、内容、标识的重复提交返回原记录；修改内容或换人复用标识会被拒绝。已有完成记录只能查看，复检需要新任务。

手工检测不能伪造生产计划、订单、领取人或来源业务。缺少生产关联的记录可保留实测，但不能确认批次数量。委外任务继续使用委外收发检验入口，通用实测入口拒绝覆盖委外任务。

标准加载后不会因窗口聚焦或网络恢复而静默更换规则。可用“重新加载”明确刷新，保留实测输入，再核对新的版本与项目后提交。

## 不合格、处置和数量分别记录

超出全部等级范围，或命中配置为不合格的等级，结果均为 `FAIL`。此时不写报废处置或报废数量。返工、让步接收、报废由异常处置流程确认。

数量结算要求任务已完成及生产计划、产品和批次关联有效。结算按钮不再先调用实测接口写入隐式 `PASS`。一次抽样不合格也不会自动把整批数量判为报废；实测、异常处置与批次数量是不同事实。

## 单一配置格式与实测记录

标准只接受 `DEVIATION_BANDS`、完整上下偏差和明确的合格判定。每个重量项目必须归属有效且启用的品质检验站。前后端解析拒绝当前契约未定义的字段，不能静默忽略未知规则内容。

实测任务提交时记录标准版本、规则快照、逐项结果和提交标识。

## 验证

- 前端品质回归覆盖规则编辑往返、非对称偏差、非法等级、只读状态、失败保留与重试、后端结果展示、历史缺失提示及数量结算不写入 `PASS`。
- Go 回归覆盖端点、无效配置拒绝、实测缺失/重复/未知/单位不符、版本及产品校验、不可覆盖历史、异常处置独立。
- PostgreSQL 使用随机独立 schema，覆盖并发重试唯一性、领取人保护、来源关联保留、标准归档后的原结果重试、审计失败整笔回滚，并回归标准审批发布事务。
- Playwright 使用真实组件与隔离服务替身，验证中文、英文、深色、桌面和窄屏，覆盖等级增删修改、保存失败保留输入、重试及快照结果。未向真实业务写入测试实测。
- 构建、TypeScript、相关 ESLint、语言键一致性、中文编码和共享控件字体约束均纳入收尾检查。
