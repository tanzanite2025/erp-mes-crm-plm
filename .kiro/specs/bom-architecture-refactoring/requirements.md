# BOM 模块架构重构 - 需求文档

## 概述

**项目名称**: BOM 模块架构重构  
**项目类型**: 技术债务清理 + 架构优化  
**优先级**: 高（P1）  
**预计周期**: 4-6 周  
**影响范围**: 后端服务 + 前端 React 组件 + 数据库

---

## 背景与动机

### 当前问题

经过全链路深度审计，BOM 模块正处于"架构腐化"的边缘，存在以下 5 个系统性问题：

1. **树投影逻辑的双重实现** - 前后端各维护一套树解析逻辑
2. **业务规则散落在审计快照中** - 审计代码承担了数据镜像职责
3. **bom_service.go 职责超载** - 830+ 行的上帝文件
4. **ID 物理变更与前端缓存冲突** - 违反 SDRTS 原则
5. **前后端校验逻辑硬编码** - 缺乏自描述性

### 业务影响

- **开发效率**: 新增字段需要在 5+ 处同步修改
- **维护成本**: 测试文件频繁因类型失同步而崩溃
- **用户体验**: 每次保存后前端必须全量重绘（性能差）
- **数据一致性**: 审计快照容易遗漏字段（已发现 SortOrder 丢失）

### 重构目标

1. **降低耦合**: 前后端职责清晰，减少重复逻辑
2. **提升性能**: 支持增量更新（SDRTS），避免全量重绘
3. **增强可维护性**: 单一职责，易于扩展
4. **保证数据完整性**: 自动化审计快照，避免手动映射

## 核心问题详细分析

### 问题 1: 树投影逻辑的双重实现

#### 现状
- **后端**: `bom_sidecar_contract.go` 实现树结构验证与规格定义
- **前端**: `bom-workspace-source-model.ts` + `use-bom-workspace-projection.ts` 重新实现树解析、层级计算、节点折叠

#### 问题
- 树协议变更需要前后端同步修改
- 前端 Hook 包含复杂的业务规则（如 `isCollapsibleCollectionSourceBranchNode`）
- 测试文件因类型失同步而崩溃

#### 影响
- **开发效率**: 新增 NodeKind 需要修改 3+ 个文件
- **一致性风险**: 前后端逻辑可能不一致
- **测试成本**: 需要维护两套测试

#### 期望
- 树投影逻辑收敛到单一位置（后端或共享 TS 工具类）
- 前端仅负责渲染，不包含业务规则

---

### 问题 2: 业务规则散落在审计快照中

#### 现状
- `engineering_audit.go` 中的 `bomAuditSnapshot` 手动映射 BOM 字段
- `BOMVersionSnapshot` 存储逻辑与审计逻辑重叠

#### 问题
- 审计文件承担了"定义数据镜像结构"的职责
- 新增字段容易在审计快照中被遗漏（如 SortOrder）
- 手动映射冗余，容易出错

#### 影响
- **数据丢失**: 历史版本无法还原完整数据
- **审计盲区**: 无法追踪某些字段的变更
- **维护成本**: 每次新增字段需要修改审计代码

#### 期望
- 审计快照自动化（利用 GORM 钩子或反射）
- 审计文件仅负责记录变更，不定义数据结构

---

### 问题 3: bom_service.go 职责超载

#### 现状
- 文件已膨胀至 830+ 行
- 集成了查询、保存、删除、派生、状态流转、循环引用检查、审计触发等所有操作
- 充斥着重复的事务模板代码

#### 问题
- 单一文件职责过多，违反单一职责原则
- 业务逻辑被事务管理和审计代码"淹没"
- 复杂逻辑（如 `DeriveMBOMFromEBOM`）容易漏掉字段同步

#### 影响
- **可读性差**: 难以快速定位业务逻辑
- **维护困难**: 修改一个功能可能影响其他功能
- **测试困难**: 难以进行单元测试

#### 期望
- 拆分为 `BOMQueryService`（只读/投影）和 `BOMCommandService`（写入/派生/状态流转）
- 提取公共的事务管理和审计触发逻辑

---

### 问题 4: ID 物理变更与前端缓存冲突

#### 现状
- `SaveBOM` 使用"物理删除 + 重新插入"模式
- 每次保存后所有 BOMItemID 都会变化

#### 问题
- 前端 `useBOMWorkspaceProjection` 依赖 BOMItemID 维持树状视图状态
- 每次保存后前端必须全量重绘
- 无法实现细粒度的增量更新（违反 SDRTS 原则）

#### 影响
- **性能差**: 大型 BOM（1000+ 行）保存后重绘耗时 > 5 秒
- **用户体验差**: 保存后丢失展开/折叠状态
- **前端复杂度高**: 需要复杂的状态恢复逻辑

#### 期望
- 重构 `SaveBOM` 为增量 Upsert
- 保证 BOMItemID 在生命周期内的稳定性
- 支持前端 SDRTS（Server-Driven Real-Time Sync）

---

### 问题 5: 前后端校验逻辑硬编码

#### 现状
- `bom_sidecar_contract.go` 中的校验逻辑
- 前端 Zod Schema 中有几乎相同的副本

#### 问题
- 校验逻辑冗余，不具备自描述性
- 后端修改必填项，前端不会收到类型层面的警告
- 运行时才能发现接口报错

#### 影响
- **开发效率低**: 需要手动同步前后端校验规则
- **一致性风险**: 前后端校验可能不一致
- **用户体验差**: 前端校验通过，后端却报错

#### 期望
- 后端提供 JSON Schema 或 OpenAPI 规范
- 前端自动生成 Zod Schema
- 或者使用共享的 TypeScript 类型定义

## 重构目标与成功标准

### 目标 1: 降低耦合

**具体指标**:
- 前后端共享逻辑减少 50%
- 树投影逻辑收敛到单一位置
- 前端 Hook 代码量减少 30%

**验收标准**:
- 新增 NodeKind 仅需修改 1 个文件
- 前端测试不再因后端类型变更而崩溃

---

### 目标 2: 提升性能

**具体指标**:
- 大型 BOM（1000+ 行）保存后重绘时间 < 1 秒
- 支持增量更新，避免全量重绘

**验收标准**:
- 保存后 BOMItemID 保持稳定
- 前端仅更新变更的节点

---

### 目标 3: 增强可维护性

**具体指标**:
- `bom_service.go` 拆分为 2-3 个文件，每个文件 < 400 行
- 审计快照自动化，无需手动映射

**验收标准**:
- 新增字段时，审计快照自动包含
- 单元测试覆盖率 > 80%

---

### 目标 4: 保证数据完整性

**具体指标**:
- 审计快照包含所有 BOM 字段
- 历史版本可完整还原

**验收标准**:
- 从历史版本还原后，数据与原始版本完全一致
- 审计日志可追踪所有字段的变更

## 非功能性需求

### 兼容性

- **向后兼容**: 重构过程中不破坏现有 API
- **数据迁移**: 如需修改数据库结构，提供迁移脚本
- **前端兼容**: 前端可以逐步迁移，不强制一次性切换

### 性能

- **响应时间**: API 响应时间不增加（目标：减少 20%）
- **数据库负载**: 数据库查询次数不增加
- **前端渲染**: 大型 BOM 渲染时间 < 2 秒

### 可测试性

- **单元测试**: 每个服务都有独立的单元测试
- **集成测试**: 覆盖关键业务流程
- **E2E 测试**: 覆盖前后端交互

### 可观测性

- **日志**: 关键操作记录详细日志
- **监控**: 添加性能监控指标（如保存耗时、查询耗时）
- **告警**: 异常情况自动告警

## 风险评估

### 高风险

1. **数据迁移失败** - 可能导致数据丢失
   - **缓解措施**: 充分测试，提供回滚方案

2. **性能下降** - 增量 Upsert 可能比物理删除慢
   - **缓解措施**: 性能基准测试，优化 SQL 查询

### 中风险

3. **前端兼容性问题** - API 变更可能导致前端报错
   - **缓解措施**: 保持 API 向后兼容，逐步迁移

4. **测试覆盖不足** - 重构后可能引入新 Bug
   - **缓解措施**: 补充单元测试和集成测试

### 低风险

5. **团队学习成本** - 新架构需要团队学习
   - **缓解措施**: 提供详细文档和培训
